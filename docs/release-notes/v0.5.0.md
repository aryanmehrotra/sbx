# sbx v0.5.0 — configurable health-check interval (`health_interval`) and a readable `sbx ui` table

Released 2026-08-18.

You can now choose how often sbx health-checks your services, for the whole sandbox or per
service. Large sandboxes no longer run dozens of probe commands a second. `sbx ui` columns now
line up whatever your names are, and CPU is shown in millicores.

## Before you upgrade

- **Behaviour change:** `sbx ui` shows CPU in millicores (`147mc`), not percent (`14.7%`), so it
  can be added up and compared with a limit written as `500m`. The suffix is `mc` because the
  column beside it uses `m` for megabytes.
  **Do this:** nothing; read `1000mc` as one full core.

## Highlights

### Choose the health-check interval with `health_interval`

Every service used to be probed every 300 ms by a command run inside its container. A sandbox
of fourteen services was about 47 container commands a second, all the time.

```json
{ "version": 1,
  "health_interval": "1s",
  "services": { "db": { "image": "postgres:16-alpine", "ports": [5432],
                        "health": "pg_isready -U app",
                        "health_interval": "300ms" } } }
```

- Set it once for the sandbox; override it on a service whose readiness you want caught quickly,
  or whose probe is expensive.
- The interval is also the floor on how long a wake appears to take. A service ready in 40 ms
  reports 300 ms at the default and one second at `1s`.
  [SPEC.md](https://github.com/aryanmehrotra/sbx/blob/v0.5.0/docs/SPEC.md) says which way to move
  it for which purpose.
- Allowed range is 50 ms to 5 m. On Kubernetes, sub-second values round up to one second (the
  API server reads zero as its default of ten).
- Checked on real containers: both the sandbox default and a per-service override arrive in
  docker's `Healthcheck.Interval`.

### A dashboard table you can read

- Every column is sized from its contents, so long `sbx-<sandbox>-<service>` names no longer
  push numbers out of line. Nothing is truncated: every port and full container name is kept.
- Each block has a heading, and STATE, CPU and MEMORY sit in the same place in both blocks.
- Traces are coloured even without a limit, relative to the service's own peak. A flat line
  stays calm.
- Every address is a clickable link in iTerm2, WezTerm, Kitty, GNOME Terminal and Windows
  Terminal (cmd- or ctrl-click). It assumes `http://`, so clicking a postgres port opens a
  browser that cannot talk to it.

## Fixes

- A sandbox of ten or more services (`14/14 up`) pushed its own row's CPU, memory and limit
  cells two columns right of their headings.
- Opening the system pane (`a`) could leave the sandbox block with no services under its
  heading. The two panes now share the space.
- A line wider than the terminal made the dashboard scroll into stacked copies of its header.
  Verified under a pty that resizes mid-run.
- Rows looked one character out in iTerm2 and others, because the "no limit" dash was drawn
  double-width. Counted columns are now ASCII only.
- Links in the table could break column widths; escape sequences are now measured consistently.

## Known limitations

- A container shares the host kernel. `--isolation gvisor|kata` can be declared and is refused
  where that runtime is absent.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.5.0 sh
go install github.com/aryanmehrotra/sbx@v0.5.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.5.0`.

Nothing to migrate. `health_interval` is optional; a spec without it behaves as in v0.4.0.
