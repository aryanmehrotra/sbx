## What your health probes cost is now a decision

Every service was probed every 300 ms. That constant was chosen when a sandbox was one database,
and it is a command started *inside* the container that runs whether or not anybody is waiting -
so a sandbox of fourteen services is about **forty-seven container commands a second, for ever**,
on a laptop whose runtime may already be busy. Nobody chose that. It was one default arriving
fourteen times.

```json
{ "version": 1,
  "health_interval": "1s",
  "services": { "db": { "image": "postgres:16-alpine", "ports": [5432],
                        "health": "pg_isready -U app",
                        "health_interval": "300ms" } } }
```

Sandbox-wide first, because the cost belongs to the fleet rather than to any one service in it,
and turning it down once beats turning it down fourteen times. A service overrides it where its
readiness is worth catching quickly or where its probe is expensive.

It is also the floor on how long a wake *appears* to take - a wake is not over until the answer
changes, and the answer is only re-evaluated on the interval - so [SPEC.md](https://github.com/aryanmehrotra/sbx/blob/v0.5.0/docs/SPEC.md)
says which way to move it for which purpose instead of leaving you to find that out from a
benchmark. A service that is ready in 40 ms reports as 300 ms at the default and as a second
at `1s`.

Two ends are refused: **under 50 ms** spends cpu to learn nothing, **over 5 m** reports a service
as still waking long after it is serving. In a cluster the sub-second case is rounded up to one
second rather than passed through as zero, because zero means "use my default" to the API server
- which is ten - so a spec asking for a *faster* probe would have quietly got a much slower one.

Checked on real containers: the sandbox default and a per-service override both arrive intact in
docker's own `Healthcheck.Interval`.

## The dashboard is a table you can actually read

`sbx ui` placed its columns by concatenation - pad this field to fourteen, that one to
thirty-four, and hope. A constant is exact until the first thing that does not fit it, and after
that every wider row carries its numbers a few characters further right. Fourteen services named
`sbx-<sandbox>-<service>` overflow both immediately, which is why a busy fleet read as a ragged
list rather than something you can run your eye down.

**Every column is measured from what is in it**, once per block, and every row is handed the same
widths. Each block has a heading over it, so a column of figures is identified where it sits
rather than by its shape. The table and the block below it share their positions for STATE, CPU
and MEMORY, because those three mean the same thing in both and a reader should not have to find
them twice on one screen.

Nothing is cut to make the sums work: a service publishing two ports keeps both, a container
keeps its whole name, and where that makes the block wider than the table, the block wins.

**CPU is millicores.** `147mc`, not `14.7%`. A percentage answers "is it busy" and cannot be
added up or held against a ceiling somebody wrote as `500m` in a spec. The suffix is `mc` rather
than the bare `m` a cluster uses, because the column beside it prints `563m` for megabytes.

**Traces are coloured even without a limit.** Nothing has a ceiling unless you set one, so most
of a fleet was drawn flat green whatever it did - the moment a service spiked was the moment the
trace still said it was fine. With no ceiling, "high" can only mean high for this service, so the
peak of the window is the reference and the colour now agrees with the height of the line. A
service that never moves is left calm: normalising a flat line to its own maximum would paint an
idle redis permanently red.

**Every address is a link.** `127.0.0.1:20002` carries no scheme, so no terminal makes it
clickable on its own. iTerm2, WezTerm, Kitty, GNOME Terminal and Windows Terminal all open one on
cmd- or ctrl-click. It assumes `http://` - the only scheme a browser can follow - so a click on a
postgres port opens a browser that cannot speak to it. That is the price of the ports where it
works.

## Fixed

- **A sandbox of ten or more services misaligned its own row.** The STATE column was a fixed six
  characters - exactly `asleep`, and two short of `14/14 up`. Everything after it is positioned by
  counting characters, so that row's CPU, MEMORY and both limit cells sat two columns right of
  their own headings, while every smaller sandbox on the same screen was correct. It is measured
  from the data now, like every other column.
- **Opening the system pane emptied the sandbox block.** `a` asks for a line per container on the
  machine, and that ask was paid first - leaving the block with its four fixed lines and not one
  service under its own `SERVICE` heading, on a block whose title read "14 services". The two now
  split the space in proportion, and the heading is drawn only where a service can follow it.
- **The dashboard could scroll itself into stacked copies of its own header.** If any line came
  out wider than the terminal, the terminal wrapped it, the frame became taller than the screen,
  and writing its last line scrolled - so every frame after it landed a row lower and never
  recovered. Autowrap is off while the dashboard owns the terminal, and it now writes no more
  lines than there are rows. Verified under a pty that resizes mid-run.
- **A table that measured perfectly still looked a character out.** The dash it drew for "no
  limit" was U+2014, which is East Asian Ambiguous - iTerm2 and others draw it double-width, so
  the terminal disagreed with the count from that dash rightward. Every character inside a counted
  column is ASCII now, and the test asserts it rather than describing it.
- **Three escape-skippers disagreed about where an escape ends.** Each stopped at the first `m`,
  which is true of every colour sequence and false of a URL. They share one implementation now,
  and so does the test helper - a stripper that disagrees with the renderer makes every assertion
  about width a guess.

## Install or upgrade

```sh
brew install aryanmehrotra/tap/sbx        # or: brew upgrade sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.5.0
```

Binaries for macOS, Linux, FreeBSD and Windows on amd64 and arm64 are attached below with
`SHA256SUMS` beside them - `install.sh` verifies it. The cluster activator is
`ghcr.io/aryanmehrotra/sbx-activator:v0.5.0`.

**Nothing to migrate.** Existing sandboxes, specs and snapshots are unchanged, and `health_interval`
is optional everywhere - a spec that does not mention it behaves exactly as it did in v0.4.0.
Every change here is either a new field you can ignore or a rendering fix.

**Still true:** a container shares the host kernel, `--isolation gvisor|kata` is declarable and
refused where the runtime is absent.
