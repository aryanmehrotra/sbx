# sbx v0.9.1 — security fix: the OpenSandbox API now always requires a key

Released 2026-09-26.

**Upgrade now if you run `sbx serve --osb-addr` without `--osb-key`.** On v0.9.0 a sandbox could
call the keyless API, read other sandboxes' execd tokens and run commands in them. Nothing else
in sbx is affected; without `--osb-addr` the API does not exist.

## What happened

v0.9.0 let the OpenSandbox API run keyless on a loopback address, because `127.0.0.1` looked
private. On colima and Docker Desktop it is not: every container reaches the host's loopback
through `host.docker.internal`, `host.lima.internal` or the VM's gateway (measured on colima from
a plain `alpine` container).

No host escape was possible: the v0.9.0 API accepts no volumes, capabilities or privileged mode.
Cross-sandbox takeover was. The full advisory, including what to do about sandboxes that ran
untrusted code on a keyless v0.9.0, is in
[SECURITY.md](https://github.com/aryanmehrotra/sbx/blob/v0.9.1/SECURITY.md#advisories).

## Before you upgrade

- **Breaking:** a key is always required. With none given, `sbx serve` generates one into
  `~/.sbx/osb/key` (mode 0600) and prints where, never the key. `sbx mcp` reads it from there.
  **Do this:** give SDK clients the key:
  ```sh
  sbx serve --osb-addr 127.0.0.1:8080 &
  export OPEN_SANDBOX_API_KEY="$(cat ~/.sbx/osb/key)"
  ```
  Keyless remains as `--osb-insecure-no-key`, loopback only, with a warning naming who can
  reach it.
- **Breaking:** a non-loopback `--osb-addr` is refused, until a server-proxy mode ships. The endpoints it returned were loopback
  listeners no remote client could use.
  **Do this:** reach the API from elsewhere with `sbx connect` or an SSH tunnel.
- **Behaviour change:** API sandboxes now carry an `sbx.osb` label, and a daemon that does not
  serve the API leaves them alone. Sandboxes created by v0.9.0 have no label.
  **Do this:** recreate API sandboxes created by v0.9.0.

## Fixes

- A sandbox could lift its own network policy: the egress sidecar route accepted the sandbox's
  execd token, which the workload holds. The sidecar now has its own per-sandbox credential that
  never enters the container.
- After a daemon restart, a paused sandbox could be thawed by a connection before the pause was
  re-applied. Pauses are now restored before any listener binds.
- `sbx sleep` / `sbx wake` on an API-paused sandbox stopped it and lost its memory. They now
  refuse and point at the API's resume.

Every fix came with a test that failed before it. A probe from inside a sandbox now gets `401` on
every route through all three host addresses, with no key and with its own token.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.9.1 sh
go install github.com/aryanmehrotra/sbx@v0.9.1
sbx doctor                        # checks this machine can run what you use
```

Then restart `sbx serve`. If your clients already passed `--osb-key`, nothing else changes.

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.9.1`.
