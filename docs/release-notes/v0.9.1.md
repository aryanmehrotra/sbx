## A security fix for the OpenSandbox API

**Upgrade if you run `sbx serve --osb-addr` without `--osb-key`.** Nothing else in sbx is
affected, and without `--osb-addr` the API does not exist.

v0.9.0 let the OpenSandbox API run keyless on a loopback address, on the reasoning that
`127.0.0.1` is private. On colima and Docker Desktop it is not: every container reaches the host's
loopback through `host.docker.internal`, `host.lima.internal` or the VM's gateway, measured on
colima from a plain `alpine` container. So a sandbox running untrusted code could call the API,
read every other sandbox's execd token, and run commands in them.

**No host escape** was possible in v0.9.0 - its API accepts no volumes, capabilities or privileged
mode - but cross-sandbox takeover was. The full advisory, including what to do about sandboxes
that ran untrusted code on a keyless v0.9.0: [SECURITY.md](../../SECURITY.md).

---

## What changes for you

**A key is now always required.** If you give none, `sbx serve` generates one into
`~/.sbx/osb/key` (0600) and says where it put it - never the key itself. `sbx mcp` reads it from
there when it talks to a local daemon, so the MCP setup keeps working unchanged. SDK clients need it:

```sh
sbx serve --osb-addr 127.0.0.1:8080 &
export OPEN_SANDBOX_API_KEY="$(cat ~/.sbx/osb/key)"
```

Keyless still exists, as `--osb-insecure-no-key`, loopback only, with a warning that names
exactly who can reach it.

**Also fixed, found in the same review:**

| | |
|---|---|
| **The egress sidecar route** | used to accept the sandbox's own execd token, which the workload holds - so a box could lift its own network policy. It now has a separate per-sandbox credential that never enters the container |
| **A non-loopback `--osb-addr`** | is refused. The endpoints it hands out are loopback listeners no remote client can use, so it only looked supported. `sbx connect` or an ssh tunnel is the way to reach it from elsewhere until server-proxy mode ships |
| **A paused sandbox after a restart** | pauses are re-applied before the daemon binds a single listener, so there is no window where a connection thaws what the API reports as Paused |
| **`sbx sleep` / `wake` on an API-paused sandbox** | refuse and point at the API's resume, instead of stopping it and losing the memory the pause kept |
| **A second daemon on the same engine** | API sandboxes carry an `sbx.osb` label and a daemon that does not serve the API leaves them alone. Sandboxes created by v0.9.0 have no label - recreate them |

Every fix came with a test that failed before it, and a probe from inside a sandbox now gets
`401` on every route through all three host addresses, with no key and with its own token.

## Adopting it

```sh
brew upgrade sbx          # or: go install github.com/aryanmehrotra/sbx@v0.9.1
```

Restart `sbx serve`. If your clients already passed `--osb-key`, nothing else changes.
