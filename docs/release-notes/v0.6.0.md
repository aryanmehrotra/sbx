## The dashboard reaches a sandbox that is not on your laptop

v0.4.0 gave `sbx connect` a deployed sandbox's ports. v0.5.0 made the dashboard worth looking at.
**v0.6.0 points the dashboard at the deployment** — the same `sbx ui`, reading a sandbox that is
somewhere else.

```sh
sbx ui --connect https://sbx.example.dev
sbx ui --connect db=https://db.example.dev --connect cache=https://cache.example.dev
```

It takes the same URLs and tokens as `sbx connect`, and several deployments merge into one screen
exactly as their ports do. There is no second dashboard to learn: `sbx ui` is written against a
provider, and a deployment reached over connect is one, so every column, trace and key works as it
does locally. The renderer never learns the difference.

---

## It controls the deployment, not just reads it

The dashboard's keys act on the sandbox over connect, each authorised by the connect token:

- **Enter wakes, `s` sleeps, `L` limits, `d` removes, `l` reads logs** — the same keys, doing the
  same things, on a sandbox that is elsewhere.
- **`f` forwards.** Over connect the address on screen is the deployment's, not this machine's — so
  it was not reachable without a separate `sbx connect` in another window. `f` binds the selected
  service's ports on `127.0.0.1` and tunnels each, so `psql` or `redis-cli` reaches a database that
  is not otherwise exposed. It keeps the service's own port where it is free, so the address the
  dashboard already showed is the one that works; it falls back to any free port and tells you the
  real one where this machine already has it; and it holds the tunnel until you quit.

This is a deliberate widening of what the connect token is worth. It once bought reading what is
fronted and a byte tunnel; it now controls the deployment, so a leaked token is a larger incident
than it was — which is why every one of these still passes through the same authenticated gate as
the fleet listing, and nothing new is reachable without it. A shell into a service (`exec`, a TTY,
file copy) stays refused: that is a larger surface than the dashboard's keys and is its own
feature, so it is a clear refusal that names where it does work rather than a half-built one.

## A deployment with no runtime still reports its own cpu and memory

A sandbox deployed to a platform that gives one container and one HTTP port has no container
runtime behind it — the platform runs the container — so there was nothing to sample, and the CPU
and MEMORY columns read `…` forever.

But sbx runs *inside* that container, and a process can always read its own cgroup. **So a fronted
deployment now reports the container's own cpu and memory** as the service's usage, and the columns
fill with no socket and no runtime. cgroup v2 and v1 both: usage as the counters the dashboard
already turns into a rate, memory against the cgroup's ceiling, and the CPU quota so the LIMIT
columns mean something too. Where the files are not there — off Linux, a host that hides them — it
reports nothing rather than a zero it did not measure.

## Fixed

- **The title no longer prints the laptop's memory as the deployment's.** Over `--connect` the
  sandboxes are on another machine, and "host 4.09g free of 16g" printed beside the deployment's
  name read as a fact about the wrong computer. Remote mode shows no host figure rather than a
  misleading one — the machine sbx runs on there would have to report itself, and a fronted
  deployment has no runtime to ask.

## Install or upgrade

```sh
brew install aryanmehrotra/tap/sbx        # or: brew upgrade sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.6.0
```

Binaries for macOS, Linux, FreeBSD and Windows on amd64 and arm64 are attached below with
`SHA256SUMS` beside them — `install.sh` verifies it. The cluster activator is
`ghcr.io/aryanmehrotra/sbx-activator:v0.6.0`.

**Nothing to migrate.** Everything here is new behaviour on `sbx ui --connect`, which was itself
new in v0.5.0; a local `sbx ui` and a plain `sbx connect` are unchanged. **The one thing to know:**
a connect token now controls the deployment through the dashboard, not only reads it — so treat it
as the credential it is, and if that is more than you want a token to carry, keep the dashboard
pointed at deployments you would already trust it against.

**Still true:** a container shares the host kernel, `--isolation gvisor|kata` is declarable and
refused where the runtime is absent.
