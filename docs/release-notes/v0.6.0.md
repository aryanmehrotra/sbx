# sbx v0.6.0 — manage remote sandboxes from `sbx ui --connect`

Released 2026-08-18.

`sbx ui` can now show and control sandboxes deployed elsewhere: the same dashboard, keys and
traces as locally. `f` forwards a remote service's ports to `127.0.0.1`. A deployment with no
container runtime still reports its own CPU and memory.

## Before you upgrade

- **Behaviour change (security):** a connect token now *controls* a deployment through the
  dashboard (wake, sleep, limit, remove, logs), not only reads it. A leaked token is a larger
  incident than before. Every action passes the same authenticated gate as the fleet listing.
  **Do this:** treat `SBX_CONNECT_TOKEN` as a full credential. Point the dashboard only at
  deployments you already trust it against.

## Highlights

### See remote sandboxes in `sbx ui`

```sh
sbx ui --connect https://sbx.example.dev
sbx ui --connect db=https://db.example.dev --connect cache=https://cache.example.dev
```

It takes the same URLs and tokens as `sbx connect`, and several deployments merge into one
screen. Every column, trace and key works as it does locally.

### Control them from the keyboard

- `enter` wakes, `s` sleeps, `L` limits, `d` removes, `l` reads logs, on the remote sandbox.
- **`f` forwards** the selected service's ports to `127.0.0.1`, so `psql` or `redis-cli` reaches
  a database that is not otherwise exposed. It keeps the service's own port when free, otherwise
  picks a free one and tells you. The tunnel lasts until you quit.

### CPU and memory from deployments with no runtime

On a platform that runs your container for you, sbx has no container runtime to ask, so the
CPU and MEMORY columns stayed at `…`. sbx now reads its own container's cgroup (v1 and v2):
usage, memory against the ceiling, and the CPU quota for the LIMIT columns. Where those files
are missing (off Linux, or hidden by the host) it reports nothing rather than a zero it did not
measure.

## Fixes

- Over `--connect`, the title no longer shows your laptop's memory as if it were the
  deployment's host. Remote mode shows no host figure.

## Known limitations

- A shell into a remote service (`exec`, a TTY, file copy) is refused over connect, with a
  message naming where it does work.
- A container shares the host kernel. `--isolation gvisor|kata` can be declared and is refused
  where that runtime is absent.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.6.0 sh
go install github.com/aryanmehrotra/sbx@v0.6.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.6.0`.

Nothing to migrate. `sbx ui --connect` is new in this release; a local `sbx ui` and a plain
`sbx connect` are unchanged. (The notes as first published said `--connect` was new in v0.5.0;
it was not.)
