# sbx v0.10.0 — OpenSandbox API: 14 ms creates from a warm pool, plus code interpreter, terminals and snapshots

Released 2026-09-26.

`sbx serve --osb-pool` keeps sandboxes pre-created, so an OpenSandbox `create` answers in about
14 ms; cold creates drop from about 4 s to about 170 ms. The API gains code-interpreter contexts,
terminals, a port proxy, snapshots, templates and volumes. Upstream's e2e suite now runs 52 tests
against sbx, up from 38, and they pass. This release includes every
[v0.9.1](https://github.com/aryanmehrotra/sbx/blob/v0.10.0/docs/release-notes/v0.9.1.md) security
fix; if you run v0.9.0 without a key, read that first.

## Before you upgrade

- **Behaviour change:** `sbx rm` now also removes the image's own data volumes (a redis's
  `/data`, a postgres data directory), which it used to leave behind with the sandbox's data in
  them.
  **Do this:** copy out anything you need before `sbx rm`.
- **Behaviour change:** API sandboxes are health-checked once a minute, and quickly only while
  starting: 12x fewer `docker exec` calls than v0.9 (116 a minute for ten sandboxes, now 10).
  **Do this:** nothing.

## Highlights

### A warm pool: `create` answers before a container could start

```sh
sbx serve --osb-addr 127.0.0.1:8080 --osb-pool python:3.11-slim=8
export OPEN_SANDBOX_API_KEY="$(cat ~/.sbx/osb/key)"
```

sbx keeps that many sandboxes of the image created, with execd answering. `create` claims one,
gives it a fresh execd token and the caller's env, and the pool refills. A request the pool can't
match exactly (volumes, a snapshot, a template, a network policy, an unknown field) takes the
normal path, so nobody gets a sandbox missing what they asked for.

Measured with `scripts/osb-bench.sh`, create through first successful command (the way
ComputeSDK's time-to-interactive benchmark times it), M4, colima 3 vCPU / 3 GiB:

| | median | p95 | success |
|---|---|---|---|
| warm pool, one at a time | **13.7 ms** | 41 ms | 10/10 |
| cold, one at a time | 207 ms | 356 ms | 10/10 |
| warm pool, 100 at once | 472 ms | 567 ms | 100/100 |

Cold creates used to cost about 4 s: 3 s asking the registry about an image already present,
the rest waiting for the SDK's next 2-second poll. Now the image is pulled only when absent and
`create` answers once running, about 170 ms.

### New through the API

| | |
|---|---|
| **Code interpreter** | Jupyter contexts per language, state kept between cells, rich results (images, HTML), interrupt. Upstream's `code_interpreter` suite: 7/7 |
| **Terminals** | PTY sessions over WebSocket: resize, one writer plus read-only viewers, replay after reconnect |
| **Port proxy** | `GetEndpoint(port)` for any port, over HTTP and WebSocket, authenticated like execd |
| **Snapshots and templates** | Snapshot a running sandbox's filesystem, create from it, name images as templates |
| **Volumes** | `pvc` as namespaced docker volumes; `host` only under roots allowed by `--osb-host-paths` |
| **Egress env** | `OPENSANDBOX_EGRESS_*` variables go to the filter, never the workload |

### Tested as people use it

`scripts/osb-usecases-e2e.sh` runs fifteen end-to-end flows against a real daemon: an agent over
MCP, an SDK coding loop, the code interpreter, idle freeze keeping memory, pause, expiry across a
daemon crash, a live egress change, snapshot and fork, volumes, a terminal, the port proxy, a
`sandbox.json` sandbox beside API ones, scope safety, ten concurrent sandboxes, and the pool.

## Fixes

- `sbx rm` said it removed an egress filter that never existed.
- `sbx history <sandbox> --json` ignored `--json` after the name.
- `sbx mcp`: cancelling a `command_run` at the wrong moment left the command running. It is now
  interrupted.
- A failed pause or resume could leave a sandbox unreachable.
- A snapshot image carried the source sandbox's live execd token.
- A host volume path could be swapped for a symlink between the check and the mount.
- `readonly_volumes` and `volume_mounts` had leaked into the public `sandbox.json` format.

Each fix came with a test that failed before it.

## Known limitations

- **Pool members are running containers.** Fifty python members held about 620 MiB here. Size
  the pool for your burst, or pass `--osb-pool-freeze` to freeze waiting members (each claim then
  pays a thaw).
- A burst of 100 cold creates was too noisy on this machine to state (6x between runs).
- **The OpenSandbox API is docker-only.** Kubernetes answers `501` with the reason.
- **Known issue:** a daemon started with `--only` is not found by `sbx sleep` / `sbx wake`
  ("never became ready"). Drive it through the API instead. (Fixed in v0.13.0.)
- **Known issue:** docker re-resolves a host volume's source on every start, so a sandbox with
  `sbx.idle=sleep` follows a symlink swapped in while asleep. The default freeze-on-idle is not
  affected. (Fixed in v0.13.0.)
- **Not implemented:** isolated sessions, the credential vault, server-proxy mode. They answer
  `501`. (These messages named a release that would add them, which v0.13.2 removed; only the
  microVM provider, in v0.11.0, arrived as named.)

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.10.0 sh
go install github.com/aryanmehrotra/sbx@v0.10.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.10.0`.

Check it yourself: `scripts/osb-conformance.sh --tier v0.10.0` and
`scripts/osb-usecases-e2e.sh`, each against a docker engine with no sandboxes on it.
