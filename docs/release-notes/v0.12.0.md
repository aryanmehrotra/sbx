# sbx v0.12.0 — OpenSandbox API on Firecracker microVMs (not yet for untrusted code)

Released 2026-09-26.

`sbx serve --provider firecracker --osb-addr …` now serves the OpenSandbox API with every sandbox
running as a microVM. SDKs, endpoints and the upstream conformance suite are the same as on
docker. **Warning:** the VMM runs as unconfined root in this release. Do not use it for untrusted
or anonymous workloads (fixed in v0.13.0).

## Before you upgrade

- **Warning:** there is no jailer in this release. The Firecracker VMM runs as unconfined root.
  **Do this:** use microVM API sandboxes only for trusted code, or upgrade to v0.13.0, which
  confines each VMM.
- **New requirement:** microVM guests are filtered per bridge (see below).
  **Do this:** run `sbx doctor`; it checks `/dev/kvm`, iptables and each bridge guard.

## Highlights

### Serve the OpenSandbox API from microVMs

```sh
sbx doctor
sbx serve --provider firecracker --osb-addr 127.0.0.1:8090
```

| Check | Result |
|---|---|
| upstream `tests/go` conformance (v0.10.0 tier) on microVMs, CI with `/dev/kvm` | **48 passed, 0 failed, 4 skipped** (skips listed in `expected.tsv`) |
| same suite on docker | 50 passed, 0 failed, 2 skipped |
| bridge guard against the real kernel (`TestGuardLive`) | pass |
| microVM end to end (`TestFirecrackerE2E`) | pass |

- **Code-interpreter images work.** The image's entrypoint runs under execd inside the VM, so
  Jupyter starts as it does in a container. The sandbox is `Running` only once Jupyter answers
  (3 min limit by default; a timeout says which part was slow).
- **Volumes:** a `pvc` volume is an ext4 block drive. Host-path volumes are refused by name
  (a microVM has no virtio-fs).
- **Snapshots** are disk-only for API sandboxes.
- The API issues each VM's execd secrets; neither the image nor the caller can choose them.
- A Failed sandbox always says why, in its status, the daemon log and the history.
- Faster root filesystem copies without reflink: only data extents are cloned. In CI the 7.4 GiB
  code-interpreter image clones in 16 s; the VM then boots and serves in 1.1 s.

Design: [the spec](https://github.com/aryanmehrotra/sbx/blob/v0.12.0/docs/superpowers/specs/2026-09-26-api-on-microvms.md).

### Each microVM's only way out is its filter

- Each bridge gets its own egress filter on its gateway. Everything else on the host is closed to
  that bridge's guests.
- By default a VM's filter refuses RFC1918, CGNAT and ULA ranges and the host's own subnets. A
  sandbox's policy cannot reopen what the host refuses.
- The bridge guard drops guest traffic before docker's port forwarding can route it, and is
  re-checked on every wake and daemon restart.

## Fixes

- Over vsock, only the first request on a connection worked; later requests on the same
  keep-alive connection arrived already cancelled, breaking Jupyter readiness and `/code` routes.
- `/etc/hosts` inside a VM now has `localhost` and the hostname, as in docker.

## Known limitations

- **Unconfined VMM** (see "Before you upgrade"). Fixed in v0.13.0.
- **No warm pool on microVMs.** `--osb-pool` is refused with the firecracker provider. Added in
  v0.13.0.
- **A copy per VM without reflink.** On filesystems without reflink each VM copies its image's
  data: about 16 s for a 7.4 GiB image in CI. XFS with `reflink=1` or btrfs clones instantly.
  (v0.14.0 removes the copy.)
- **No bare-metal benchmark yet.** The only numbers claimed are above.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.12.0 sh
go install github.com/aryanmehrotra/sbx@v0.12.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.12.0`.

Nothing changes for docker or Kubernetes, or for API servers already running on docker.
