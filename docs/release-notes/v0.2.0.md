## Somewhere to look, and somewhere to start

v0.1.0 could run sandboxes but could not show you any. This release is the two halves of that:
a live dashboard for what is already running, and a guided start for when nothing is.

```sh
sbx ui                                 # every sandbox, awake or not, with cpu and memory
sbx init                               # pick a template, answer two questions, go
sbx history                            # what changed, and every wake and sleep
brew install aryanmehrotra/tap/sbx     # and a way to install it that is not `go install`
```

---

## `sbx ui` — a live dashboard

Every sandbox, whether it is awake, what it is costing in cpu and memory, and what the daemon
has been doing, refreshed every second. Arrows move, `enter` wakes, `s` sleeps, `l` reads logs,
`d` removes after asking, `q` quits.

The parts worth knowing, because each one is a decision rather than an omission:

- **`enter` wakes by connecting to the service**, because connecting is the only way anything
  wakes here. Calling the provider's `Start` would demonstrate a path no user has.
- **An asleep service shows a dash, not a zero.** Zero is a measurement, and there is nothing
  running to measure - which is the entire claim this project makes. An awake service whose
  sample has not arrived yet shows the same, for the same reason: a stats call that failed is
  not evidence that a database is using no memory.
- **cpu is a rate**, so the provider hands back raw counters and the dashboard divides them
  over the interval it actually redrew at. A provider returning "17%" would have had to choose
  that interval itself, and be wrong for every caller.
- **Where there is no terminal it prints the table once**, so `sbx ui | grep` does something
  sensible instead of failing.
- **Still no dependencies.** Raw mode is an ioctl and about thirty lines; the only
  per-platform part is two constant names that differ between Linux and the BSDs. Windows has
  neither, says so, and prints the table - all eight published targets build.

The update notice is read from a cache and never fetched while drawing: the request happens in
the background at most once a day, affects only the next run, does not run in CI, and
`SBX_NO_UPDATE_CHECK=1` turns it off. A dashboard that stutters to tell you about a patch
release has made itself worse than the release it is advertising.

## Getting started, and getting unstuck

- **`sbx init` is guided.** It picks a template and writes `sandbox.json` rather than printing
  a spec at you and leaving the redirect to you. `sbx init > sandbox.json` still works and is
  now the scripting path rather than the one a person takes.
- **Per-command help.** `sbx <command> --help` explains one command, and `--help` prints to
  stdout so it can be piped.
- **Errors say what to do next**, which is the difference between "never became ready" and a
  message that names the health command and its exit code.
- **`sbx history`** records what changed and every wake and sleep, with secrets redacted. It
  reads a file, so it still works when docker does not.

## Fixed

- **A failed listing is not an empty fleet.** With docker unreachable the dashboard showed
  "no sandboxes yet" and the connection error at the same time. Nothing was found because
  nothing could be looked at, and telling somebody whose daemon is down that their fleet is
  empty sends them to create a sandbox instead of to start docker.
- The daemon's log output no longer has a ragged left edge.

## Install

```sh
brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.2.0
```

The release toolchain is pinned to an exact Go patch from this release on. Go embeds its own
version in every binary it builds, so "1.26" - whatever patch is newest that day - means the
same tag rebuilds to different bytes. v0.1.0 was built with 1.26.5 and a laptop on 1.26.3 could
not reproduce it; pinned, it reproduces bit for bit from a different host OS and architecture.
Reproducible builds need the toolchain named, not just the flags.
