# sbx v0.14.0 — hardened microVMs: per-VM network namespace, file-size limits, no per-VM image copy

Released 2026-09-27.

A jailed Firecracker VMM (the process that runs one microVM) now runs in its own network
namespace and cannot write a file larger than it needs. New VMs share the image read-only
instead of copying it, and a slow sleep no longer loses a VM's memory. Nothing changes on docker or Kubernetes.

## Before you upgrade

These apply to microVM hosts only.

- New requirement: `ip netns` (iproute2, a writable `/var/run/netns`, `CONFIG_NET_NS`,
  `CONFIG_VETH`). Without it a jailed microVM is refused. Do this: run `sbx doctor`. Inside a
  container that forbids namespaces, move sbx to the host or accept the risk with `SBX_FC_JAILER=off`.
  See [TROUBLESHOOTING.md](https://github.com/aryanmehrotra/sbx/blob/v0.14.0/docs/TROUBLESHOOTING.md).
- New requirement: a custom guest kernel needs `CONFIG_OVERLAY_FS=y`. The pinned kernels have
  it. Do this: otherwise set `SBX_FC_ROOTFS=copy` to keep v0.13's full-copy layout.
- Behaviour change: a VM's writes are bounded by `SBX_FC_DISK_SIZE` (default 10G, sparse).
  Do this: raise it for a workload that writes more, or write to a volume.
- Behaviour change: VMs and snapshots made before v0.14.0 keep their full copy. On a new VM,
  volumes start one drive later (`vdd`). Do this: nothing, unless something addresses drives by name.

## Highlights

- Each jailed VMM runs in its own network namespace, holding only its tap, with no address and no route.
- Each jailed VMM has a file-size limit of its largest drive plus 64 MiB, then it is killed.
- A new VM hard-links the image read-only and writes to its own sparse layer, instead of copying the image.
- An unconfirmed sleep is asked again (10 s, 20 s, 30 s). If still unconfirmed, the VM keeps running
  and retries. After three in a row it stops as before.
- [SECURITY.md](https://github.com/aryanmehrotra/sbx/blob/v0.14.0/SECURITY.md) lists the capabilities
  the daemon needs. No VMM holds any capability, checked in CI.
- CI saw 153 VMMs, each chrooted, in its own namespace, with its own uid. Upstream conformance on
  microVMs: 48 passed, 0 failed, 4 skipped.
- Create-to-first-command is unchanged within runner noise:
  [BENCHMARKS.md](https://github.com/aryanmehrotra/sbx/blob/v0.14.0/docs/BENCHMARKS.md).

## Known limitations

- The daemon runs as root. It does privileged work on every create and wake.
- No quota on the whole state filesystem. Put `SBX_FC_STATE` on its own filesystem or enable project quotas.
- No bare-metal benchmark. The helper-VM path has not been re-run on a Mac since v0.11, and never on Windows 11.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.14.0 sh
go install github.com/aryanmehrotra/sbx@v0.14.0
sbx doctor                        # checks /dev/kvm, the jailer, iptables, the bridge guards
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached with `SHA256SUMS`.
The Windows build is useful only inside WSL2. Cluster activator: `ghcr.io/aryanmehrotra/sbx-activator:v0.14.0`.

Full changelog: https://github.com/aryanmehrotra/sbx/compare/v0.13.2...v0.14.0
