# sbx v0.14.0 — hardened microVMs: per-VM network namespace, file-size limits, no per-VM image copy

Released 2026-09-27.

A jailed Firecracker VMM (the process that runs one microVM) now runs in its own network namespace and cannot write a file larger
than it needs. New VMs share the image read-only instead of copying it, and a slow sleep no longer
loses a VM's memory. This closes two of the gaps v0.13.0 listed. Nothing changes on docker or
Kubernetes.

| | v0.13 | v0.14 |
|---|---|---|
| a jailed VMM's network | the host's namespace | **its own namespace**: only its tap, no address, no route |
| largest file a compromised VMM can write | unbounded | **its largest drive + 64 MiB**, then the VMM is killed (SIGXFSZ) |
| a new VM's root filesystem | a copy of the image | **the image, read-only and shared**, plus its own sparse layer |
| a sleep that is not confirmed | the VM stops and wakes cold | **asked again** (10 s, 20 s, 30 s); if still unconfirmed, the VM keeps running and retries |

## Before you upgrade

These apply to microVM hosts only.

- **New requirement:** the host needs `ip netns`: iproute2, a writable `/var/run/netns`, and
  `CONFIG_NET_NS` plus `CONFIG_VETH` (every distribution kernel has them). A host that cannot make
  a namespace now refuses a jailed microVM, and the error quotes `ip`.
  **Do this:** run `sbx doctor`. If sbx runs inside a container that forbids namespaces, move it
  to the host or accept the risk with `SBX_FC_JAILER=off`. See
  [TROUBLESHOOTING.md](https://github.com/aryanmehrotra/sbx/blob/v0.14.0/docs/TROUBLESHOOTING.md).
- **New requirement:** a custom guest kernel needs `CONFIG_OVERLAY_FS=y`. The pinned kernels
  have it.
  **Do this:** otherwise set `SBX_FC_ROOTFS=copy` to keep v0.13's full-copy layout.
- **Behaviour change:** a VM's writes are bounded by `SBX_FC_DISK_SIZE` (default 10G, sparse).
  **Do this:** raise it for a workload that writes more, or write to a volume.
- **Behaviour change:** VMs and snapshots made before v0.14.0 keep their full `rootfs.ext4`;
  only new creates are layered. On a layered VM, volumes start one drive later (`vdd`).
  **Do this:** nothing, unless something addresses volume drives by device name.

## Highlights

### A network namespace per VM

With the jailer on, each VMM runs in `/var/run/netns/sbxfc<slot>-<index>`. The namespace holds
only its tap (owned by the VM's uid), bridged through a veth into the sandbox's guarded bridge,
with no address and no route. A VMM escape reaches what the guest reaches, not the host network.
Unjailed (`SBX_FC_JAILER=off`) there is no namespace.

### A file-size limit per VMM

A jailed VMM runs with a file-size limit (`RLIMIT_FSIZE`) of the largest file it may legitimately
write plus 64 MiB. It bounds each file, not how many; see "Known limitations".

### New VMs share the image instead of copying it

A create hard-links the image's cached `rootfs.ext4` read-only as its base, and gives the VM an
empty, sparse writable layer of `SBX_FC_DISK_SIZE`. The guest lays overlayfs over both. Snapshots
link the base and clone only the layer. v0.12.0 measured about 16 s per create to copy the
7.4 GiB code-interpreter image on a CI runner; a layered create hard-links it instead.

### A sleep that can't be confirmed keeps the VM's memory

Sleep is asked up to three times, with a longer bound each time. If none is confirmed, the VM
stays running with its memory and gets fresh credentials, and the next idle check tries again.
After three unconfirmed sleeps in a row it stops as before, so a guest cannot keep its memory by
stalling forever.

### The daemon's privileges, written down

[SECURITY.md](https://github.com/aryanmehrotra/sbx/blob/v0.14.0/SECURITY.md) lists the
capabilities the daemon needs and why, for hosts that bound it with `CapabilityBoundingSet=`. No
VMM holds any capability (effective capabilities 0, checked in CI).

### What proves it

CI on the merged code, GitHub-hosted runner with `/dev/kvm` and the jailer on:

| Check | Result |
|---|---|
| `fc-jail-watch` across every microVM step | **153 VMMs** seen, each chrooted, in its own network namespace, with a uid no other VMM had |
| upstream `tests/go`, the files sbx targeted at v0.10.0, on microVMs | 48 passed · 0 failed · 4 skipped |
| the same, with a warm pool on microVMs | 27 passed · 0 failed · 1 skipped |
| docker: the same files · `pool` · `e2e` | 50 · 0 · 2, 20 / 20, and 3 / 3 |
| real jailer, microVM e2e, pool e2e, host guard | pass |

The e2e test checks the VMM's `/proc/<pid>/ns/net` is its VM's namespace, with no routes; the
real-jailer test reads `Max file size` from `/proc/<pid>/limits`. Create to first command
(4 concurrent, 3 rounds, `node:22-slim`) is unchanged within runner noise: 144 ms frozen pool,
759 ms asleep pool, 2,637 ms cold (v0.13: 141, 699, 2,821). That image is too small to show the
layered root's gain.

## Known limitations

- **The daemon runs as root.** It does privileged work on every create and wake, so it cannot
  drop root after starting.
- **No quota on the whole state filesystem.** Put `SBX_FC_STATE` on its own filesystem or enable
  project quotas. `sbx doctor` warns when it shares `/`.
- No bare-metal benchmark. The helper-VM path has not been re-run end to end on a Mac since v0.11
  (colima), and has never run on a Windows 11 host.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.14.0 sh
go install github.com/aryanmehrotra/sbx@v0.14.0
sbx doctor                        # checks /dev/kvm, the jailer, iptables, the bridge guards
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64; the Windows build is useful only
inside WSL2) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.14.0`.
