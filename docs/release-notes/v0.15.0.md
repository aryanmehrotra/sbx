## `sbx install`: doctor says what is missing, install puts it there

**v0.15.0 adds one command.** `sbx doctor` has always reported what this machine lacks, including
the gVisor, Kata and checkpoint rows that `--isolation` and `sbx checkpoint` refuse without. Then it
left you to find out how to install each one. `sbx install` does that part: it shows every command
first and asks before it runs any.

```sh
sbx doctor                       # ends with: missing and installable here: redis-cli, checkpoint, gvisor
sbx install gvisor --dry-run     # the exact commands, and nothing else
sbx install gvisor               # asks, then does it, then runs doctor again
sbx install                      # everything missing that can be installed here
```

`sbx doctor` itself still changes nothing.

| | what `sbx install` does |
|---|---|
| **gvisor** | fetches gVisor release 20260921.0, **pinned by sha512** (amd64, arm64), unpacks it whole under `/usr/local/lib/sbx/gvisor/`, registers it with dockerd as `runsc`, and **reloads** dockerd, so running containers are untouched |
| **checkpoint** | installs `criu`, sets `experimental: true`, and **restarts** dockerd (the plan warns first), then runs `criu check` and warns if this kernel cannot checkpoint |
| **kata** | the distribution's `kata-containers` package (dnf) registered as `kata-runtime`; needs `/dev/kvm` |
| **tools** | docker, kubectl, cloudflared, redis-cli, mkfs.ext4, iptables, from apt-get, dnf, pacman, apk or brew |

Each runtime is merged into `/etc/docker/daemon.json`, keeping everything already there. The
previous file is saved as `daemon.json.sbx-bak`.

---

## What proves it

Run on Ubuntu 24.04 with dockerd 29.3.1, starting from no runtimes, no criu and no redis-cli:

| check | result |
|---|---|
| `sbx install`, answering **n** | nothing installed, nothing written |
| `sbx install`, answering **y** | redis-cli and criu installed; gVisor fetched, **sha512 OK**, registered; doctor `✓ isolation gvisor`, `✓ docker checkpoint` |
| `sbx create --template web-stack --isolation gvisor` | both containers `runtime=runsc`; `dmesg` inside shows gVisor's kernel; Postgres and Redis answer |
| `sbx sleep`, then a plain `redis-cli get` | woken from 0 B in **0.37 s**, the key intact, still on `runsc` |
| a non-root user with sudo | the plan prefixes `sudo`; the install goes through it; a second runtime merges into the existing `daemon.json` |

CI (`test`, `e2e`, `usecases`, `isolation`, `microvm`, `osb-conformance` and the rest) passed on
the merged code.

## ⚠️ What it will not do, and what is not yet proven

- **It will not touch a daemon inside a VM.** On Docker Desktop, colima or Rancher Desktop, the
  daemon's config belongs to the VM's manager, which rewrites it on the next start. On those
  hosts, and so on every Mac, the runtimes are refused with that reason. Tools still install
  through brew.
- **Checkpoint is installed, not proven.** The test machine's kernel cannot run CRIU (`criu check`
  fails), so no checkpoint and resume was taken there. On such a kernel doctor still shows
  `✓ docker checkpoint`, because it reads only the daemon's flag. `sbx install` now says so.
  Ubuntu 24.04 dropped `criu`; the plan skips it and names `ppa:criu/ppa`.
- **Not run for real:** Kata (no `/dev/kvm` on the test machine), the dnf, pacman, apk and brew
  paths (unit-tested only), and a restart through systemd. Without systemd, install stops at the
  restart step and says to restart dockerd yourself.
- **Kata from upstream** is not offered. Its release is on GitHub and is not pinned here yet, so
  outside dnf the plan points to Kata's own docs.

## Adopting it

```sh
brew upgrade sbx          # or: go install github.com/aryanmehrotra/sbx@v0.15.0
sbx doctor                # the last line names what `sbx install` can add here
sbx install --dry-run     # read the plan before running anything
```

Nothing else changed. No flag, spec field or port moved.
