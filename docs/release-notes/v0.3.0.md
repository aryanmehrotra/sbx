## A sandbox you can reach from a laptop that is not running it

Until now sbx ran your services on the machine in front of you. That is the right default and
it stays the default - but it assumes the machine can afford four containers, and not every
machine can. **v0.3.0 separates where a sandbox runs from where you use it.** Deploy the
service to any platform that gives you one container and one HTTP port, and keep connecting to
`127.0.0.1` as though nothing had moved.

Everything else in this release is the dashboard growing up: limits beside usage, a trace per
service, and a key to change a ceiling without leaving the screen.

## Sandboxes somewhere else

![How sbx connect works: psql dials 127.0.0.1:5432, sbx connect carries that TCP stream over one authenticated HTTPS WebSocket to the single port the platform routes, and sbx serve --front hands it to a postgres that is never published.](https://raw.githubusercontent.com/aryanmehrotra/sbx/ae69c8753b24fa8e87076c130a734669c11e7e5d/docs/connect.svg)

```sh
sbx pack --spec sandbox.json           # a build context per service, under sbx-pack/

# deploy sbx-pack/db/ to your platform, with SBX_CONNECT_TOKEN set in its environment

SBX_CONNECT_TOKEN=… sbx connect https://db.example.dev
#   db  ->  127.0.0.1:5432

psql -h 127.0.0.1 -p 5432             # a database in someone else's datacentre
```

**`sbx pack`** writes the image a platform will actually run: the base image's **own** start
line - read out of the image rather than guessed - beside sbx fronting its ports. A wrapper
that invented an entrypoint would work for postgres and be quietly wrong for the next thing
anybody packed.

**`sbx connect`** turns that back into ordinary local ports. It binds `127.0.0.1` only, on the
same port numbers the deployment uses, so the `sbx env` block from over there is already
correct here and your tools never learn that anything changed.

**`sbx serve --connect-addr :8080 --front db=5432`** is the other end. `--front` offers a port
that is not a sandbox at all, so sbx can sit beside a workload in the same container - which is
what makes a platform-as-a-service, with its single HTTP port, into somewhere a database can
live. The transport is a WebSocket because an L7 proxy will strip anything more exotic.

Four things to know before relying on it:

- **One deployment per service, today.** `--front` carries several ports at once, so one
  container can serve a whole sandbox - but `pack` writes one image per service, so two
  services are two deployments and two `sbx connect`.
- **No volume means no data.** Most platforms replace the container rather than keep its disk.
  Right for a branch's fixtures, wrong for anything you would miss.
- **The token is the whole of the security.** Anyone with the URL and `SBX_CONNECT_TOKEN` has
  the port, from anywhere. sbx refuses to start the endpoint without one.
- **It is a network away.** Every round trip now costs what the internet costs.

## The dashboard

![The sbx dashboard: every sandbox and service with its state, cpu and memory against the limit it is allowed, a trace of each over time, recent wake and sleep events, and key hints along the bottom.](https://raw.githubusercontent.com/aryanmehrotra/sbx/v0.3.0/docs/ui.svg)

`sbx ui` now answers "is this bad?" rather than only "what is the number":

- **What it is allowed, beside what it is using.** A number on its own means nothing; 380 MB
  against a 512 MB ceiling means something. Colour follows the usage at that moment.
- **A trace per service.** Where cpu and memory have been, in the row itself, with units -
  percentage, peak, ceiling and span - and coloured where it happened rather than where it is.
- **`L` sets a limit from the keyboard**, offering the sizes rather than demanding a syntax.
- **`^Z` gives the terminal back**, and `fg` takes it again - a dashboard should not be the one
  program on your machine that ignores job control.

## Also new

- **`mounts`** in the spec: a host directory the sandbox writes to and you can open in your
  editor. Checked on both sides by `sbx doctor`, because a mount that Docker Desktop is not
  sharing appears in `docker inspect` and is empty inside the container.
- **Limits on kubernetes**, with a provider that says *which* permission it is missing when the
  cluster refuses rather than reporting a ceiling it never set.
- **`SBX_CONNECT_ADDR`, `SBX_FRONT` and `SBX_CONNECT_TOKEN`** are read from the environment,
  because a platform gives you environment variables and not a command line.
- **A deployed sbx with no container runtime stays up and says why**, instead of exiting and
  leaving the platform to report a healthy service that answers nothing.

## Fixed

- The data race the detector had been failing every build over.
- `sbx url` picked cloudflared's control-plane URL instead of the tunnel's.
- The selected row in `sbx ui` was the one row whose meters lied.
- Trend rows drifted out of alignment; traces moved when nothing had changed.
- Names that were shortened now admit it, and the hints tell the truth about what a key does.
- `sbx pack` explained its pinned version with an argument that a release makes false.

## Install or upgrade

```sh
brew install aryanmehrotra/tap/sbx        # or: brew upgrade sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.3.0
```

Binaries for macOS, Linux, FreeBSD and Windows on amd64 and arm64 are attached below, with
`SHA256SUMS` beside them - `install.sh` verifies it, and a download nobody can check is a
download nobody should run. The cluster activator is `ghcr.io/aryanmehrotra/sbx-activator:v0.3.0`.

**Nothing to migrate.** Existing sandboxes, specs and snapshots are unchanged. One thing to
check: if you hand-wrote a deployment that installs `sbx@main` for the tunnel, pin it to
`@v0.3.0` now that a release carries it - `sbx pack` does this for you.

**Still true:** a container shares the host kernel, `--isolation gvisor|kata` is declarable and
refused where the runtime is absent.
