# sbx v0.3.0 — run a sandbox on any container platform, use it on localhost (`sbx connect`)

Released 2026-08-17.

A sandbox no longer has to run on the machine you use it from. Deploy a service to any platform
that gives you one container and one HTTPS port, then `sbx connect` maps it back to `127.0.0.1`.
The dashboard also shows usage against limits.

## Before you upgrade

- Existing sandboxes, specs and snapshots are unchanged. Do this: if a hand-written deployment
  installs `sbx@main` for the tunnel, pin it to `@v0.3.0`. `sbx pack` does this for you.

## Highlights

```sh
sbx pack --spec sandbox.json                         # a build context per service, under sbx-pack/
# deploy sbx-pack/db/ with SBX_CONNECT_TOKEN set in its environment
SBX_CONNECT_TOKEN=… sbx connect https://db.example.dev   # db -> 127.0.0.1:5432
```

- `sbx pack` writes the image the platform runs, keeping the base image's own start command.
- `sbx connect` binds `127.0.0.1` only, on the deployment's own ports, so `sbx env` output stays correct.
- `sbx serve --connect-addr :8080 --front db=5432` is the other end, over a token-authenticated WebSocket.
- `SBX_CONNECT_ADDR`, `SBX_FRONT` and `SBX_CONNECT_TOKEN` are read from the environment.
- `sbx ui` shows each service's usage against its limit, a CPU and memory trace, and `L` to set a limit.
- A new `mounts` field in `sandbox.json` shares a host directory. `sbx doctor` checks both sides.
- Resource limits apply on Kubernetes. A refusal names the missing permission.

## Fixes

- `sbx url` picked cloudflared's control-plane URL instead of the tunnel's.
- In `sbx ui`, the selected row's meters were wrong and traces moved when nothing changed.
- A data race that failed race-detector builds.

## Known limitations

- One deployment per service: two services are two deployments and two `sbx connect` commands.
- Most platforms replace the container instead of keeping its disk. Without a volume, data is lost.
- The token is the whole of the security. Anyone with the URL and `SBX_CONNECT_TOKEN` has the port.
- A container shares the host kernel. `--isolation gvisor|kata` is refused where that runtime is absent.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.3.0 sh
go install github.com/aryanmehrotra/sbx@v0.3.0
sbx doctor
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached with `SHA256SUMS`.
Cluster activator: `ghcr.io/aryanmehrotra/sbx-activator:v0.3.0`.
