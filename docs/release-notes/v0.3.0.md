# sbx v0.3.0 — run a sandbox on any container platform, use it on localhost (`sbx connect`)

Released 2026-08-17.

A sandbox no longer has to run on the machine you use it from. Deploy a service to any platform
that gives you one container and one HTTPS port, then `sbx connect` maps it back to `127.0.0.1`.
The dashboard also shows usage against limits, a trace per service, and `L` to change a limit.

## Highlights

### Run a service elsewhere, reach it on `127.0.0.1`

![How sbx connect works: psql dials 127.0.0.1:5432, sbx connect carries that TCP stream over one authenticated HTTPS WebSocket to the single port the platform routes, and sbx serve --front hands it to a postgres that is never published.](https://raw.githubusercontent.com/aryanmehrotra/sbx/ae69c8753b24fa8e87076c130a734669c11e7e5d/docs/connect.svg)

```sh
sbx pack --spec sandbox.json           # a build context per service, under sbx-pack/

# deploy sbx-pack/db/ to your platform, with SBX_CONNECT_TOKEN set in its environment

SBX_CONNECT_TOKEN=… sbx connect https://db.example.dev
#   db  ->  127.0.0.1:5432

psql -h 127.0.0.1 -p 5432
```

- **`sbx pack`** writes the image the platform runs. It keeps the base image's own start command,
  read from the image rather than guessed, with sbx serving its ports beside it.
- **`sbx connect`** binds `127.0.0.1` only, on the deployment's own port numbers. The `sbx env`
  output from the deployment is already correct on your laptop.
- **`sbx serve --connect-addr :8080 --front db=5432`** is the other end. `--front` serves a port
  that is not a sandbox, so sbx can sit beside a workload in one container. The transport is a
  token-authenticated WebSocket, because L7 proxies strip anything more unusual.
- `SBX_CONNECT_ADDR`, `SBX_FRONT` and `SBX_CONNECT_TOKEN` are read from the environment, because
  a platform gives you environment variables, not a command line.
- A deployed sbx with no container runtime stays up and says why, instead of exiting.

### See usage against limits in `sbx ui`

![The sbx dashboard: every sandbox and service with its state, cpu and memory against the limit it is allowed, a trace of each over time, recent wake and sleep events, and key hints along the bottom.](https://raw.githubusercontent.com/aryanmehrotra/sbx/v0.3.0/docs/ui.svg)

- Each service shows what it uses beside what it is allowed (for example 380 MB of 512 MB).
- A CPU and memory trace per service, in the row, with units, peak, ceiling and span.
- `L` sets a limit from the keyboard, offering sizes to pick from.
- `^Z` suspends the dashboard and `fg` brings it back.

### Share a host directory with `mounts`

A new `mounts` field in `sandbox.json` gives a sandbox a host directory you can open in your
editor. `sbx doctor` checks both sides, because a directory Docker Desktop is not sharing looks
mounted but is empty inside the container.

### Limits on Kubernetes

Resource limits now apply on the Kubernetes provider. When the cluster refuses, the error names
the missing permission.

## Fixes

- `sbx url` picked cloudflared's control-plane URL instead of the tunnel's.
- In `sbx ui`, the selected row's meters were wrong; trend rows drifted out of alignment and
  traces moved when nothing had changed.
- Shortened names now show that they are shortened, and key hints describe what each key does.
- A data race that failed race-detector builds.

## Known limitations

- **One deployment per service.** `--front` can carry several ports, but `sbx pack` writes one
  image per service, so two services are two deployments and two `sbx connect` commands.
- **No volume means no data.** Most platforms replace the container instead of keeping its disk.
  Fine for a branch's fixtures, wrong for data you would miss.
- **The token is the whole of the security.** Anyone with the URL and `SBX_CONNECT_TOKEN` has the
  port, from anywhere. sbx refuses to start the endpoint without a token.
- **It is a network away.** Every round trip costs what the internet costs.
- A container shares the host kernel. `--isolation gvisor|kata` can be declared and is refused
  where that runtime is absent.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.3.0 sh
go install github.com/aryanmehrotra/sbx@v0.3.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.3.0`.

Nothing to migrate: existing sandboxes, specs and snapshots are unchanged. If you hand-wrote a
deployment that installs `sbx@main` for the tunnel, pin it to `@v0.3.0`; `sbx pack` does this
for you.
