## A sandbox spread across several deployments is still one set of local ports

v0.3.0 put a sandbox somewhere else and left you to reassemble it by hand. `sbx pack` writes
one image per service, so a platform that gives you one container per deployment turned a
two-service sandbox into two deployments, two `sbx connect` commands, two port maps and two
things to remember. **v0.4.0 takes as many endpoints as you have and gives back one port map.**

```sh
sbx connect db=https://db.example.dev cache=https://cache.example.dev
#   db     ->  127.0.0.1:5432
#   cache  ->  127.0.0.1:6379

psql -h 127.0.0.1 -p 5432        # one command, and the sandbox is whole again
```

The joining happens on the laptop, where it is free. The alternative - one container running
everything - is worse than it sounds: two images cannot generally be merged, and grafting redis
into `postgres:16-alpine` works only because both are musl. The same graft into `postgres:16`
builds cleanly and dies at runtime with `redis-server: not found`, because the binary is there
and its loader is not. That is a deployment that looks healthy until somebody connects. Each
service keeps the image its spec named.

Three things this needed beyond a loop:

- **A token per deployment.** Two deployments usually have two. A named endpoint reads
  `SBX_CONNECT_TOKEN_<NAME>` before falling back to the shared `SBX_CONNECT_TOKEN`, rather than
  forcing one secret across both.
- **Clashes named.** Two deployments fronting 5432 - two postgres, a normal thing to want -
  used to surface as `address already in use`, which reads as something outside sbx taking the
  port. It now says which two wanted it and how to move one: `--port-offset replica=1000` moves
  only that one, `--port-offset 1000,replica=2000` moves everything with an exception.
- **Fleets fetched together.** A deployment wakes on its first request, so asking three in turn
  would pay a cold start three times. One failure still fails the whole command: a port map
  with holes is how somebody reaches their own laptop believing they reached the remote.

Tested end to end against the real binary - two deployments, two tokens, one connect, and bytes
that arrive at the right upstream rather than the other one.

## The dashboard learned what a sandbox is

`sbx ui` listed services, so a sandbox with four of them was four lines repeating one name -
while `sbx env`, `sbx rm` and `sbx logs` all name a sandbox and not a service. **`v` folds the
table up.**

```
  SANDBOX              CONTAINS    STATE      CPU   MEMORY  CPU LIMIT        MEMORY LIMIT
› zopnight-today-work  2 services  2/2 up    7.6%   365 MB  [█·········] 1.5c [█████·····] 640m
```

- **`2/2 up`, not AWAKE.** A row standing for four services where one is running is a fair
  summary of the cost and a bad summary of the state.
- **Its own ceiling and its own trace.** The limit is the sum of its services', and the graph is
  their usage added together at each moment - so the meter, the percentage and the peak all mean
  the sandbox. A sum counts only where *every* service has a ceiling: three capped and a fourth
  without is a sandbox nothing bounds, and the total of the three would be a figure that looks
  like a limit and holds nothing back.
- **`L` caps the whole sandbox** - every service at the value typed. The prompt says "each
  service in work", because capping each at 512m and sharing 512m between them are different
  instructions and the number is the same either way.
- **Enter and s act on all of it**, at once rather than in turn: waking four services one after
  another costs the sum of four cold starts.

**It shows the machine, not just the fleet.** The title carries "sbx 1017m of 7.74g · host
4.39g free of 16g" - two different computers on macOS and Windows, each labelled, because the
VM's ceiling and the laptop's are different numbers and an unlabelled pair reads as one machine
described twice. `a` opens a pane for the machine itself: every container on it, ours or not,
ranked by what it is holding, with ours and everything else totalled apart. A dashboard listing
only its own services reports a nearly empty machine while the VM is full, which is the state
this was written on. It is sampled only while that pane is open, because it costs a round trip
per running container.

**Each service inside a sandbox shows its own share.** 41.2% of a sandbox reading 44.7% says
which service is working; 354m of 387m said only which was resident. Both readings sit under the
table's own CPU and MEMORY columns, and a service publishing two ports no longer drags its line
out of the column the others share.

**An empty dashboard now says what to do.** A machine with no sandboxes got one line above a
screen of nothing, under a row of keys that every one of them acts on a row which is not there.
It offers the two commands that make one, and - where there is a record to point at - says how
much history outlived the sandboxes that made it. Sandboxes are removable and their history is
not, so answering "there are none" while 349 events sit in the pane below reads like amnesia.

## One behaviour change to know about

**`sbx connect` refuses `http://` to anything but this machine.** The token is the whole of the
security of a tunnel, and plain HTTP sends it as text to everything in between; the server half
has always refused to serve a connect endpoint off loopback without `--behind-proxy`, and the
client had no matching rule. Use the `https://` URL your platform gave you. A loopback address -
a `kubectl port-forward`, a local daemon, a test - is unaffected and needs nothing.
`SBX_CONNECT_INSECURE=1` waives it for a network you have decided to trust.

## For anything driving sbx

`sbx list --json` - the first thing a script or an agent asks, and the one surface that had no
machine-readable form, so the answer was a regex over column widths. `doctor`, `env` and
`history` already had one. An empty fleet is `[]` rather than prose, so "there are none" and "I
could not look" stay different answers.

[docs/AGENTS.md](https://github.com/aryanmehrotra/sbx/blob/v0.4.0/docs/AGENTS.md) is new: a
block to paste into a project's `AGENTS.md` or `CLAUDE.md` so Claude, Codex or anything else
reaches for a sandbox instead of `docker run`, followed by the four things they get wrong and
the list of what sbx refuses and why.

It also writes down something that already worked and was nowhere: **a box to run your own
commands in**. `sbx exec` drops you into the service you name, and a service image holds the
service and nothing else - so a shell with your code in it is a service you declare, with your
toolchain as the image and `mounts` putting the repository in it. It sleeps like everything
else, and `exec` wakes it.

## Fixed

- **A URL written after a flag was dropped without a word.** `sbx connect db=… --port-offset
  1000 cache=…` connected `db`, printed the single-deployment listing and never mentioned
  `cache` - a port map with a hole in it, which is how somebody reaches their own laptop's
  sandbox believing they reached the remote one. Refused now, naming what would have been lost
  and printing the line that works.
- **An empty deployment says which kind of empty it is.** `--sandbox` was blamed for any
  deployment that came back with nothing, including one that was fronting nothing in the first
  place - which sent people to check a filter that had changed nothing for it. The error names
  the filter only where some deployment actually had services taken from it, and both the
  aggregate error and the per-deployment line now ask that same question rather than two
  different ones.
- **An offset landing on port 0** bound a random port while the listing still said `:0`, because
  `net.Listen` reads 0 as "give me any free port". Offsets that leave 1-65535 are refused, and
  the message names the one that did it.
- **Two deployments whose names differ but whose environment variables do not** - `db-1` and
  `db_1` both read `SBX_CONNECT_TOKEN_DB_1` - silently shared one token. Refused, naming the
  variable they collide on.
- **The fleet request had no timeout and no size bound**, so a deployment that accepted and then
  said nothing wedged the whole command with no output. Sixty seconds, matching the docker
  client, and a megabyte cap on a reply that lists ports.
- **A URL carrying a password came back out in errors** in full, where Go's own wrapped error
  redacts it. The auth here is the bearer header and the userinfo is ignored, so it was exposure
  without a purpose.
- **A data race in the dashboard** that had been failing `go test -race` on main.
- **A slow container runtime said "context deadline exceeded"**, which describes what the Go
  runtime did rather than what happened. Measured at 1m36s to list seven containers on a loaded
  colima: it now says docker did not answer in time, and points at the two things worth
  checking, because a daemon that is slow and one that is absent need different fixes.
- **A sandbox of five services listed four** and said nothing about the fifth, because the
  detail block asked for a fixed five lines whichever kind of row was selected.

## Install or upgrade

```sh
brew install aryanmehrotra/tap/sbx        # or: brew upgrade sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.4.0
```

Binaries for macOS, Linux, FreeBSD and Windows on amd64 and arm64 are attached below, with
`SHA256SUMS` beside them - `install.sh` verifies it, and a download nobody can check is a
download nobody should run. The cluster activator is `ghcr.io/aryanmehrotra/sbx-activator:v0.4.0`.

**Almost nothing to migrate.** Existing sandboxes, specs and snapshots are unchanged, and a
single-URL `sbx connect` still means exactly what it did in v0.3.0 - the name on an endpoint is
optional and only earns its keep once there are two. If you pinned a deployment to `sbx@v0.3.0`
for the tunnel, `sbx pack` moves it forward for you.

**The one thing to check** is above: a `sbx connect` command pointing at an `http://` URL that is
not on this machine now stops rather than sending your token in the clear. That is the only
invocation this release turns away that v0.3.0 accepted.

**Still true:** a container shares the host kernel, `--isolation gvisor|kata` is declarable and
refused where the runtime is absent, and this has not been run in production outside its own
test suite.
