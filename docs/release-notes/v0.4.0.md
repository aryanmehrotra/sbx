# sbx v0.4.0 — one `sbx connect` for a sandbox spread over several deployments

Released 2026-08-17.

`sbx connect` now takes several deployments at once and gives back one local port map, so a
two-service sandbox is one command again. `sbx ui` groups services into sandboxes and shows what
is using the machine's memory. Scripts and agents get `sbx list --json`.

## Before you upgrade

- **Breaking:** `sbx connect` refuses a plain `http://` URL to anything but this machine. The
  token is the whole of a tunnel's security, and plain HTTP sends it in clear text. Loopback
  addresses (`kubectl port-forward`, a local daemon, a test) are unaffected.
  **Do this:** use the `https://` URL your platform gave you, or set `SBX_CONNECT_INSECURE=1` for
  a network you have decided to trust.

## Highlights

### Connect to several deployments with one command

```sh
sbx connect db=https://db.example.dev cache=https://cache.example.dev
#   db     ->  127.0.0.1:5432
#   cache  ->  127.0.0.1:6379

psql -h 127.0.0.1 -p 5432
```

- **A token per deployment.** A named endpoint reads `SBX_CONNECT_TOKEN_<NAME>` before falling
  back to the shared `SBX_CONNECT_TOKEN`.
- **Port clashes are named.** Two deployments that both serve 5432 now get an error saying which
  two, and how to move one: `--port-offset replica=1000` moves only that one;
  `--port-offset 1000,replica=2000` moves everything, with an exception.
- **Deployments are fetched together**, so three sleeping deployments pay one cold start, not
  three. If one fails, the whole command fails: a port map with holes is worse than none.
- Each service keeps the image its spec named; the joining happens on your laptop.

Tested end to end against the real binary: two deployments, two tokens, one connect.
Walkthrough: [USE-CASES.md](https://github.com/aryanmehrotra/sbx/blob/v0.4.0/docs/USE-CASES.md) ·
what the token protects: [SECURITY.md](https://github.com/aryanmehrotra/sbx/blob/v0.4.0/SECURITY.md)

### See sandboxes, not just services, in `sbx ui`

Press `v` to fold services into one row per sandbox:

```
  SANDBOX              CONTAINS    STATE      CPU   MEMORY  CPU LIMIT        MEMORY LIMIT
› checkout-today-work  2 services  2/2 up    7.6%   365 MB  [█·········] 1.5c [█████·····] 640m
```

- State reads `2/2 up`, not AWAKE, so a partly running sandbox is visible.
- The sandbox's limit is the sum of its services' limits, and only shown when every service has
  one. Its trace is their usage added together.
- `L` caps every service in the sandbox at the value you type. `enter` and `s` wake or sleep all
  of its services at once.
- Inside a sandbox, each service shows its share of the sandbox's CPU and memory.
- An empty dashboard offers the two commands that create a sandbox, and says how much history
  is still on record.

### See what is using the machine's memory

The title shows sbx's usage and the host's free memory, for example "sbx 1017m of 7.74g · host
4.39g free of 16g". On macOS and Windows those are two machines (the VM and the laptop), and each
is labelled. Press `a` for every container on the machine, sbx's or not, ranked by memory. It is
sampled only while that pane is open, because it costs a round trip per running container.

### `sbx list --json` for scripts and agents

```sh
sbx list --json
```

An empty fleet is `[]`, so "there are none" and "I could not look" stay different answers.
`doctor`, `env` and `history` already had JSON output.

### Guidance for AI coding agents

[docs/AGENTS.md](https://github.com/aryanmehrotra/sbx/blob/v0.4.0/docs/AGENTS.md) is new: a block
to paste into a project's `AGENTS.md` or `CLAUDE.md` so Claude, Codex and others use a sandbox
instead of `docker run`. It lists the four things agents get wrong and what sbx refuses, and why.
It also documents a pattern that already worked: declare a service whose image is your
toolchain, use `mounts` to put the repository in it, and `sbx exec` into it. It sleeps like any
other service, and `exec` wakes it.

## Fixes

- `sbx connect db=… --port-offset 1000 cache=…` silently dropped `cache` (a URL after a flag).
  It is now refused, with the command line that works.
- A deployment that returned no services always blamed `--sandbox`. The error now names the
  filter only when it actually removed something.
- An offset that landed on port 0 bound a random port while the listing said `:0`. Offsets that
  leave 1–65535 are refused, naming the one responsible.
- Two deployment names that map to the same variable (`db-1` and `db_1` both read
  `SBX_CONNECT_TOKEN_DB_1`) silently shared a token. Now refused, naming the variable.
- A deployment that accepted and then said nothing hung `sbx connect`. The fleet request now
  times out after 60 seconds and caps the reply at 1 MB.
- A URL containing a password was printed in full in errors. It is now redacted.
- A slow container runtime reported "context deadline exceeded". It now says docker did not
  answer in time and what to check. (Measured: 1m36s to list seven containers on a loaded colima.)
- A sandbox of five services listed only four in the dashboard's detail block.
- A dashboard data race that failed `go test -race` on main.

## Known limitations

- A container shares the host kernel. `--isolation gvisor|kata` can be declared and is refused
  where that runtime is absent.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.4.0 sh
go install github.com/aryanmehrotra/sbx@v0.4.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.4.0`.

Existing sandboxes, specs and snapshots are unchanged, and a single-URL `sbx connect` means what
it did in v0.3.0. If you pinned a deployment to `sbx@v0.3.0`, `sbx pack` moves it forward.
