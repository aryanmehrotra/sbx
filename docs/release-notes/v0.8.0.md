## A stack that sleeps, and the addresses that say whether anyone is listening

v0.7.0 gave the agent box its controls. **v0.8.0 is about the sandbox with more than one service
in it** — the shape where sleep-on-idle had been quietly unusable. A dependency could not be
reached by the name the spec calls it, and the reaper could take one away from a service still
using it. Both produced the same `no such host`, which is what made them expensive.

Along the way: `sbx url` stopped being refused by the dev servers it exists to share, stopped
taking a port from the daemon it depends on, and the listings stopped claiming an address when
nothing owns it.

Everything below was measured on a live sandbox. The numbers are from those runs.

---

## A service answers to its own name

`depends_on: ["db"]` woke db correctly, and then a dependent configured with `db:6379` failed
anyway. Docker's embedded DNS knew only the container — `sbx-<sandbox>-<service>` — while every
other part of sbx calls it `db`: the key in `services`, `depends_on`, `sbx logs`, `sbx exec`.

```
nslookup db              ->  NXDOMAIN
nslookup sbx-deplab-db   ->  172.19.0.2
```

A service on a sandbox network now carries its own name as a network alias. Measured with a
dependent dialling once a second: **ok=0 failed=23 before, ok=20 failed=0 after.**

The error it produced was `no such host` — the same words as the wake bug fixed in v0.7.0 — so it
read as a regression of something that was actually fine. That is most of why it is worth its own
entry.

---

## The reaper stopped sleeping a dependency that was in use

Dependency-ordered *wake* landed in v0.7.0. Nothing stopped the reaper from re-creating the same
condition afterwards: it consulted each unit's own idle clock and never `depends_on`.

A dependency is used over the sandbox's own network, which the daemon is not on. The dependent
dials it directly, so not one of those bytes reaches a proxy leg and the dependency's idle clock
runs out **while it is under constant load**. With `--idle 45s`, an `app` polled every 15s and a
`db` never touched directly:

```
t= 45s  ok=60  failed=0
t= 60s  ok=72  failed=4     <- db slept underneath it
t= 75s  ok=83  failed=8
t= 90s  ok=94  failed=12    <- +4 every 15s, indefinitely
```

and `sbx list` said `db awake` throughout.

The reaper now skips a service that an awake service depends on. **165 seconds, zero new
failures.** A stack sleeps from the top down instead of all at once — dependents idle out first,
their datastores become eligible a tick later — and it still reaches 0 B: `app slept - idle for
54s`, then `db slept - idle for 45s` a minute after, both containers at 0 B, and one connection
brings the pair back in **0.18s**.

A `depends_on` cycle leaves both members awake. Holding memory is recoverable; cutting a live
dependency is not.

---

## `sbx url` works on the dev servers it exists to share

A tunnel rewrites `Host` to its own hostname, and every dev server that checks the header refuses
it. Measured against a real vite:

```
curl direct                                ->  200
curl -H 'Host: <name>.trycloudflare.com'   ->  403
  Blocked request. This host (...) is not allowed.
```

Same class in webpack-dev-server, Rails and Django. Sharing a branch preview is the entire point of
`sbx url`, and the most common thing to share was the thing that did not work.

The service is now sent `Host: 127.0.0.1:<port>` and the command says so. `--host-header pass`
sends the public hostname instead, for a service that needs its real name — absolute links, an
OAuth callback, a cookie domain. Only cloudflared can do this; ngrok removed the flag in v3 in
favour of a traffic-policy file, so asking for it there is an error naming cloudflared rather than
a silent no-op.

---

## `sbx url` stopped taking a port from the daemon

cloudflared's metrics listener takes the first free port of **20241–20245**. sbx hands out
**20000–21199**, so that range is sandbox slot 12. With nothing on those ports, cloudflared binds
20241 and the daemon can no longer listen on it — an intermittent `bind: address already in use`
that only appears on the day slot 12 is the one being allocated, caused by the command you ran to
share a preview.

It is now started with `--metrics 127.0.0.1:0`, an ephemeral port, which is outside the range by
construction.

---

## A listing says when nothing owns the addresses it prints

The ADDRESS column is the daemon's ports, not docker's — docker publishes a backing port and `sbx
serve` owns the public one. With no daemon, every address in the table refuses while the table
still says `awake` and prints them.

Reported as a live case: the dashboard showed a service **AWAKE on 127.0.0.1:20020 holding
567 MB**, and the browser said "refused to connect". Both were true, and nothing on the screen
reconciled them.

`sbx list` now says so under the table, and `sbx ui` carries `no sbx serve` on its top line. Only
for a local fleet: a deployment reached over `sbx connect` is fronted by the sbx running there, and
this machine's daemon says nothing about it.

---

## `egress_allow` works where it used to refuse

The allow-list is enforced by a filtering proxy the daemon binds **on the sandbox's bridge
gateway**. On colima and Docker Desktop that gateway lives inside the Linux VM while `sbx serve`
runs on the host, so the bind cannot succeed:

```
listen tcp 172.20.0.1:20999: bind: can't assign requested address
```

The consequence was a warning every refresh tick against a sandbox that had been reported created:
the service came up healthy and had **no egress at all** — not even to the allowed hosts. Measured
from inside such a box: `api.anthropic.com -> 000`, `example.com -> 000`. It failed closed, which
is the safe direction and the wrong report.

The first fix was a refusal: probe the gateway and say no, with the reason and the way out, the
same way `--isolation gvisor|kata` and `egress: "deny"` on kubernetes are refused rather than
silently approximated. It named the real fix as absent — "running the filter as a container on the
sandbox network instead of as a host listener".

**That is now what happens, and the refusal is gone.** Where the daemon can hold the gateway it
still binds it, because a listener in the process that already knows which units are awake is the
simpler arrangement. Where it cannot, sbx builds a small image from **its own filter source** —
the same file the unit tests and fuzz targets cover, with only its package clause rewritten — and
runs it on the bridge. Once per machine; the tag is a hash of the build context, so a changed
filter rebuilds and an unchanged one is found in the cache.

The container is dual-homed, which is what makes it a bastion rather than a hole: the sandbox's
no-NAT bridge on one side, an ordinary bridge on the other. The workload keeps no route out of its
own. Measured on a Mac, where this used to refuse outright:

| from inside an allow-listed box | result |
|---|---|
| `wget http://example.com/` (on the list) | the page |
| `wget http://neverssl.com/` (not on the list) | `403 Forbidden`, from the filter |
| the same fetch with `HTTP_PROXY` unset | timed out — no route at all |

Against a **remote** `DOCKER_HOST` the filtering works too, but the activity signal does not: the
filter publishes its last-activity timestamp on the docker host's loopback, which is that machine's
and not yours. sbx does not publish the port there rather than refuse the whole feature over it.

## An allow-listed box stays awake while it works

The box an agent works inside is the one nothing dials. It reads files, edits them, compiles and
calls a model API, and sbx sleeps a service on the bytes through its port - so on the only measure
sbx had, such a box looked idle from the moment it started working. The window closed mid-task and
the container stopped. The single setting that avoided it was `idle: "never"`, which holds the
box's memory for as long as the sandbox exists: the cost sbx exists to avoid, reintroduced by the
feature meant to make agent boxes usable.

One of those four things is visible. A box with `egress_allow` reaches the outside through a
filtering proxy sbx already runs, so **its calls out now count as activity**. A box that is
working stays awake; one whose agent has stopped sleeps on the ordinary timer and drops to 0 B.

Stamped on bytes rather than on connections - a streaming response that takes four minutes to
arrive keeps the box awake for four minutes, where a stamp per connection would have slept it at
minute one. Throttled to one stamp a second per gateway, because stamping takes the daemon lock
and an idle window is measured in minutes. A **refused** request stamps nothing, so a box looping
against a blocked host cannot hold its own memory open.

Measured: **+2.1 ns per 32 KiB chunk, zero allocations.** Proven with a real container and a real
`HTTP_PROXY` reaching an allow-listed host, and with a blocked host stamping zero.

It does not help a box with no allow-list, or one calling out over something that is not HTTP.
There `idle: "never"` is still the answer.

## Also in this release

- **Dependency-ordered wake** (`fb02e29`) — a connection woke only what it addressed, so a woken
  service dialled a stopped peer and died on `no such host`. On a fourteen-service sandbox, six
  services died that way within a minute of their datastores being slept. `depends_on` is now
  walked before a start, independent siblings wake in parallel, and a cycle is broken rather than
  hung on.
- **A stale awake belief is revoked** (`116e61e`) — a dependency stopped out of band stayed
  believed-awake indefinitely, because nothing dials a dependency from the daemon and so nothing
  corrected the belief. Discovery already had the real state every tick and now uses it.
- **The audit trail records who** (`1ffddc8`) — a slept or removed sandbox says which actor did it,
  not only that it happened.

## Upgrading

Nothing in a `sandbox.json` changes and no existing spec needs editing. Two behaviours are
different and both are visible when they happen:

- `sbx url` rewrites the Host header by default. `--host-header pass` restores the old behaviour.
- `sbx create` refuses `egress_allow` on a VM-backed docker instead of creating a sandbox whose
  allow-list is not enforced. `egress: "deny"` needs no proxy and still works everywhere.

A multi-service sandbox that had `idle: "never"` throughout to work around the sleep problem can
drop it now, and get its memory back when it is not in use.

```sh
brew install aryanmehrotra/tap/sbx        # or: brew upgrade sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.8.0
```

## Found by reviewing this release, and fixed in it

A multi-model review pass over the changes above turned up six more, two of them in the new
code and one that predates it and is the most serious thing in this release.

### A branching dependency graph could kill the daemon

`wakeAll` shares one visited set across the whole recursion and wakes siblings in parallel. The
set was a bare map, and the only mutex in `wakeAll` is a fresh local one per invocation — so two
siblings that each have their *own* dependencies descend into `wakeAll` at the same moment and
write that map concurrently. Go answers a concurrent map write with `fatal()`, which no recover
catches: **`sbx serve` dies, and every sandbox on the machine loses its ports.**

It takes a graph that branches into further dependencies to reach at all — `gateway` on `api`
and `worker`, each with a datastore — so every existing test, all chains and one two-cycle,
missed it. A fourteen-service stack is exactly the shape that has it.

The set now carries its own lock. The regression test builds that branching graph and fails
with `WARNING: DATA RACE` without the fix.

### A dependency woken for someone else could be slept before they finished starting

Nothing dials a dependency through the proxy, so no byte ever reaches its leg — and `wakeSelf`
never stamped the idle clock. A unit woken only as a dependency therefore came up already past
the idle window, and the reaper could stop it inside the window where its dependent was still
starting, before that dependent was awake and protecting it. `no such host`, through the one
door still open after the reaper learned to respect `depends_on`.

Waking counts as activity now - including when the dependency was already up, which is the
common case in a running stack and the half the first version of this fix missed: wakeSelf
returns at its already-awake fast path, and the reaper builds its protected set only from units
that are already awake, so for the length of the dependent's start the dependency sat in
neither.

### `sbx url --via ssh` refused to run at all

`--host-header` defaults to `rewrite`, ssh can never rewrite, and the check fired on the value
rather than on whether anyone had asked — so `sbx url x web --via ssh`, the form that works with
nothing installed, errored out instead of running. ssh is explicit-only, so that was the only
way to reach it: the backend this package keeps for the machine that has no tunnel installed was
broken outright.

Only an explicit `--host-header rewrite` is refused now. A default nobody typed is a preference,
not a requirement.

### `sbx ui` went stale, and lied to a cluster

Two in the new warning. It was computed once when the dashboard opened, so a daemon that died
mid-session left the title claiming everything was fine while every address on screen had
started refusing — reproducing the exact bug the line was added to catch, on the one surface
that is long-lived. And both `sbx ui` paths checked only `--connect`, so a kubernetes fleet —
woken by its in-cluster activator, nothing to do with a daemon here — was told no daemon was
running. `sbx list` had this right through `isLocal`; the dashboard did not.

The decision is now asked every tick, from one function both paths share.

### `egress_allow` left a half-built sandbox

The gateway check landed inside per-service creation, and services are created one at a time
with no rollback — so a spec whose third service carried the allow-list left the first two
running and the sandbox half-built, with a retry that failed in exactly the same place. It is
asked once now, before anything is created.

### `sbx list | grep -q` exited 141

The daemon warning above was written to stdout, after the table. Asking whether a daemon is
running reads a file and signals a pid — long enough for `grep -q` to have matched, exited and
closed the pipe, and the write that followed took SIGPIPE and killed the process. The table was
printed correctly every time; only the exit status was wrong, which is the kind of break a
script notices and a person does not.

It goes to stderr now, where a note about the answer belongs — `2>/dev/null` is exactly how a
caller says it wants the data and not the commentary.

Found by the use-case suite, driving the tool the way the README tells someone to. Twelve
packages of unit tests, the race detector, 4.4 million fuzz executions and a fourteen-job CI run
had all passed it.

## The connection got cheaper

Profiling the hot path found the cost is not where the docs look. The relay is genuinely
zero-allocation and the published ~15 µs overhead reproduces exactly — **13.15 µs direct against
27.79 µs proxied**. But **opening** a connection costs 4.8× what a round trip on it costs, and 27
of the 38 allocations it charged were one line: `net.DialTimeout` taking a fixed endpoint,
formatting it with `Sprintf`, parsing it back, walking the resolver and building a deadline
context and timer — per connection, forever, for an address that cannot move.

A leg's upstream is resolved once now. Measured on one machine, n=6, 400 connections a sample:

| | allocs/op | B/op |
|---|---|---|
| before | 65 | 38.6 KB |
| after | **47** | **37.5 KB** |

**−18 allocations and −1.1 KB per connection.** Not a latency win, and not claimed as one: the
medians are 118.8 µs and 125.6 µs against a 107–159 µs spread.

Only a literal address is pinned. A name is looked up on every dial, because that is what a name
is for — and it keeps the timeout, because loopback either connects or refuses at once while a
cluster Service with no endpoints blackholes.

A connection-churn benchmark ships with it. This package had none: both existing benchmarks hold
one socket open for the whole run, which amortises the dial to nothing — which is how a
27-allocation dial sat in the hot path beside a docs section celebrating the zero-allocation
relay. What sbx is for is `psql` and `redis-cli`: connect, do one thing, close.

### One measurement that did not reproduce

`BENCHMARKS.md` says 64 KiB is the relay buffer's measured sweet spot and that "128 and 256 KiB
were both slower and far noisier". On an M4 that does not hold: 256 KiB is **+9.7%** with
variance as tight as 64 KiB's, and under the doc's own `GOMAXPROCS=4` condition 64 KiB was the
**slowest** row of the sweep. The committed sweep stops at 256 KiB, so it cannot see its own knee.

The buffer is unchanged at 64 KiB. Raising it to 256 KiB would take the pool from 128 KiB to
512 KiB per live connection, against a daemon that advertises 9.1 MB at rest — a
throughput-for-memory trade worth making deliberately, or not at all.

### A fork is safe to interrupt

Killing `sbx fork` part-way through could leave a sandbox that was **present, healthy, and
serving the wrong data** — the one outcome a fork must never produce. `scripts/interrupt-e2e.sh`
states the invariant ("either correct or cleanly gone") and it failed intermittently, in CI and
locally, on two different rounds.

The order was the whole of it. Fork called `Create`, which starts every service to health-check
it — so a database initialised an empty data directory and served from it — and only then copied
the snapshot over the top. Between those two steps the fork existed and had the wrong data.

The volumes are filled first now, before anything can run on them. Interrupted during the copy,
no sandbox exists and the volumes are orphans `sbx gc` collects. Interrupted inside `Create`,
every service that exists is already sitting on the snapshot's data. There is no ordering left
that produces the bad state — and no live data directory to overwrite, so the restore no longer
stops anything.

**Measured: interrupt-e2e at five rounds, twice — 30/0 then 31/0.** Ten kill-rounds clean,
against two failures in about six before. `fork-e2e` still 9 of 9.

### The relay buffer stays 64 KiB, for a reason that now holds

`BENCHMARKS.md` said 64 KiB was the measured throughput knee. It is not — the sweep stopped at
256 KiB, inside the climb. Extended to 1 MiB, **256 KiB is +38% and the knee is near 512 KiB**;
the old numbers do not reproduce on an M4 under either condition, including the `GOMAXPROCS=4`
one they were taken under, where 64 KiB is the *slowest* row.

The size is unchanged, and the justification is replaced with the true one: measured against the
daemon's own RSS under 60 concurrent streams, 256 KiB costs **+10 MiB** (15→33 vs 15→23) — more
than doubling the footprint of a tool whose whole claim is that an idle sandbox costs nothing,
to buy bandwidth the workload cannot use. At 4.9 GB/s the database is already the binding
constraint, not the proxy.

`soak.sh` sees no difference between the two, because it drives connections one after another.
That is the measurement to distrust here, not the one to quote — and the sweep now runs past its
own knee so it can never again conclude something its data does not contain.

## What testing this release added, and what it found

Three gaps in how sbx is tested were closed, and each found something.

**Fuzzing, on four parsers that had none.** `sandbox.json` is the one file a person writes by
hand and the one an agent generates; `${VAR}` expansion reads values from outside it; a sandbox
name becomes a container name, a volume name and part of a DNS label; and the ports label is
sbx's own state, read back off a container it did not necessarily write. 1.5M executions on the
spec loader, 3.2M on names, no crash — but the ports label gave up a real one, below.

**`sbx connect`, end to end, for the first time.** It is the only surface reachable from off the
machine, and nothing ran it: the unit tests cover the frame parser and the allow-list, and the
live proof was done once by hand against a deployment and never repeated.
`scripts/connect-e2e.sh` needs no cloud account — the "deployment" is a second sbx on loopback,
which is the code path a platform runs. It checks that `/healthz` answers without a credential,
that the fleet is refused without a token, with a wrong token and with a token in the query
string, that the local port map is opened, and that a payload larger than one relay chunk
survives whole.

**A port that cannot be bound is refused.** `ParsePorts` accepts any integer, so a corrupted or
hand-edited `sbx.ports` label carrying `0` reached the daemon — and `net.Listen` reads port 0 as
"any free port", so the daemon would bind an arbitrary one, log that it was listening, and front
the service at an address nothing will ever dial, while `sbx env` handed out 0. Failure by
succeeding.

The parser is deliberately *not* tightened: a label it refuses makes the container invisible to
`sbx list` **and** `sbx rm`, which is a sandbox nobody can clean up. The value stays visible and
removable, and `unit.serve` refuses it at the one place where acting on it would be silent.

### A half-close survives `sbx connect` now

`write; shutdown(SHUT_WR); read` — `nc -N`, an HTTP client sending `Connection: close`, a Go
`io.Copy` pipeline — did not work through the tunnel. Measured against an echo workload: direct
returned `ECHO:hello`, through `sbx connect` it returned **empty with a nil error**. The answer
truncated to nothing and reported as a clean EOF, which is the worst way for it to fail.

TCP has a half-close and a WebSocket does not — its close is bidirectional — so both relays tore
the whole tunnel down the moment their read side ended, killing the direction that still had the
reply to deliver.

A zero-length binary frame carries the signal now. It is free to mean this: both relays only
ever write a frame when they read more than zero bytes, so one has never been sent by the data
path, and it needs no new opcode — which matters because an L7 proxy in the middle understands
ordinary binary frames and may not understand a reserved one. Whichever direction finishes
second closes the tunnel, so neither can cut the other off.

Old deployments stay correct. The fleet response advertises `halfClose`, and a client only sends
the signal to a deployment that asked for it — against an older sbx, which would write the empty
frame upstream as a no-op and never deliver the EOF, the client keeps the previous behaviour
rather than turning a truncated reply into a wait.

### Every command is now run by something

Ten had no end-to-end coverage — `init`, `with`, `wake`, `ui`, `url`, `pack`, `history`,
`connect`, `checkpoint` and `resume`. `usecases-e2e.sh` walks the documented journeys, which is
the right shape for a suite and leaves exactly this gap: a command nobody wrote a use case
around is a command nothing runs, so a regression in any of them reached a release with every
gate green.

`scripts/commands-e2e.sh` is deliberately shallow — does it run, does it answer, does it refuse
what it should — because a shallow test that exists beats a deep one that does not. It checks
the things worth pinning: that `sbx with` returns *the command's* exit status, since CI gates on
it; that `sbx ui` without a terminal still prints the fleet; that `sbx url` refuses an unknown
`--via` and an unknown `--host-header` without opening a tunnel to the internet; and that
`checkpoint` refuses with a reason off Linux, which is the behaviour a mac can actually prove.

Two things it taught, both written into it:

Assertions capture output and match with a shell pattern rather than piping to `grep -q`. Under
`set -o pipefail` a `grep -q` that matches early closes the pipe, the command takes SIGPIPE, and
the pipeline reports **141** — a test that fails because it succeeded. Two of these read exactly
that way first time.

And it needs a pause after the `with` cases remove their sandboxes. On a VM-backed docker the
host-side port forward can outlive its container by seconds, so a create straight after an `rm`
gets a slot whose ports docker has not released and the container never binds. That is
`TROUBLESHOOTING.md`'s documented condition reproducing on demand, not a defect in the commands.

### `sbx create` works on kubernetes again

Every template declares a health command, and sbx runs it as soon as the workload exists to tell
a missing binary apart from one that is merely early — waiting two minutes to say "never became
ready" for a command that is not in the image is the least useful message this tool can produce.

On kubernetes the pod is still scheduling at that moment, and the apiserver answers
`unable to upgrade connection: container not found ("app")`. That contains the words *not found*,
which the classifier matched — so `sbx create --provider kubernetes` failed **every template with
a health check** and reported *"the health command cannot run in this image"*, telling the reader
to go and check whether the tool was installed.

Measured in a real minikube against `nginx:alpine`: `wget` is at `/usr/bin/wget` and the exact
command exits `0` a moment later. A wrong diagnosis that sends somebody to fix the wrong thing is
worse than no diagnosis, and this one rejected a spec that was correct.

Only the shell decides now. Exit status 127 and 126 are its own verdicts, and the text match is
narrowed to the shell's wording (`sh: wget: not found` — with the colon) so it cannot catch a
runtime talking about a container. The container-lifecycle messages every runtime produces while
starting — kubernetes' `container not found`, `ContainerCreating`, `PodInitializing`, docker's
`is not running` and `No such container` — are excluded first, because waiting is exactly what
fixes them.

Verified on minikube after the fix: create, `list`, `env`, `wake` scaling 0 → 1 and reporting
serving, `sleep`, and `rm`. The activator scaled the sandbox to zero on its own idle timer, which
is the whole claim. The documented refusals hold too — `build:` in a spec, `egress: "deny"` and
`sbx url` are each declined with the reason rather than approximated.

`deploy/Dockerfile` now says how to build it. `activator.yaml` asks for `sbx-activator:dev` and
nothing recorded that the image needs `deploy/` as the build context and a Linux binary placed
there first — so the first thing anyone tries fails on a missing `entrypoint.sh`.
