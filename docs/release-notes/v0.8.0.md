## A sandbox with more than one service in it, and a box that works for a living

v0.7.0 gave the agent box its controls. **v0.8.0 makes them work on the machines most people are
on, and makes a multi-service sandbox sleep properly for the first time.**

If you have been holding a stack open with `idle: "never"` because sleeping it broke things, or
you gave up on `egress_allow` because your Mac refused it, both of those are fixed here.

Every number below is from a live run. The [engineering log](v0.8.0-engineering.md) has the
measurements, the failures found on the way, and what each fix cost.

---

## A stack sleeps and wakes as a stack

Two bugs made a multi-service sandbox quietly unusable, and both produced the same `no such
host`, which is what made them expensive to tell apart.

**A service now answers to its own name.** `depends_on: ["db"]` woke db correctly and then the
dependent, configured with `db:6379`, failed anyway — docker's DNS knew only
`sbx-<sandbox>-<service>`. Measured with a dependent dialling once a second: **ok=0 failed=23
before, ok=20 failed=0 after.**

**The reaper stopped sleeping a dependency that was in use.** A dependency is reached over the
sandbox's own network, which the daemon is not on, so its idle clock ran out *while it was under
constant load*:

```
t= 60s  ok=72  failed=4     <- db slept underneath a live app
t= 90s  ok=94  failed=12    <- +4 every 15s, indefinitely
```

A stack now sleeps from the top down and still reaches **0 B**, and one connection brings the
pair back in **0.18s**.

**If you set `idle: "never"` on a stack to work around this, you can drop it** and get the memory
back when nobody is using it.

## `egress_allow` works on your Mac

The allow-list is enforced by a filtering proxy on the sandbox's bridge gateway — and on colima,
Docker Desktop, rootless docker and a remote `DOCKER_HOST`, that gateway lives inside a VM the
daemon cannot reach. Which is every Mac.

sbx now runs the same filter as a small container on the bridge instead. Same code, built from
sbx's own source, so the two cannot drift apart. Measured from inside a box, on a Mac, where this
used to be refused outright:

| | |
|---|---|
| a host on the list | the page |
| a host not on the list | `403`, from the filter |
| the same fetch with `HTTP_PROXY` unset | timed out — **no route at all** |

The filter is dual-homed, so it is a door rather than a hole: the workload still has no route out
of its own.

## A box that only calls out is a box that is working

The box an agent works in is the one nothing dials. It reads files, compiles, and calls an API —
all invisible to a proxy that measures inbound bytes. So it looked idle from the moment it started
working, and the only escape was `idle: "never"`, which holds its memory for the sandbox's whole
life.

One of those things is visible. **An allow-listed box's calls out now count as activity.**

```json
{ "image": "python:3.12", "ports": [7777],
  "egress_allow": ["api.anthropic.com", "pypi.org"], "idle": "10m" }
```

Verified with the box driving its own traffic and never touched: **awake through twelve
consecutive 30-second idle windows** while calling out, and a plain service beside it slept on
schedule at 60s. Stamped on bytes, so a four-minute streaming response keeps it awake for four
minutes. Cost: **2.3 ns per 32 KiB, zero allocations.**

## `sbx url` works on the dev servers it exists to share

A tunnel rewrites `Host`, and every dev server that checks it refuses:

```
curl direct                                ->  200
curl -H 'Host: <name>.trycloudflare.com'   ->  403
```

Same in vite, webpack-dev-server, Rails and Django — so the most common thing to share was the
thing that did not work. The service now gets `Host: 127.0.0.1:<port>`; `--host-header pass`
sends the public name for anything that needs it (absolute links, an OAuth callback).

It also stopped taking a port from the daemon. cloudflared's metrics listener grabbed 20241,
inside sbx's own range, causing an `address already in use` that only appeared on the day slot 12
came up.

## New, behind feature gates

Each is off until you ask for it. `sbx features` lists what this build has; there is deliberately
no switch for all of them.

```sh
SBX_FEATURES=ssh sbx ssh my-task
```

- **`sbx ssh`** — reach a sandbox with VS Code Remote-SSH, Cursor or JetBrains Gateway. No new
  mechanism: the SSH connection *is* what wakes the sandbox. A sleeping sandbox woken by
  `ssh-keyscan` in **0.255s**.
- **`sbx init --from-devcontainer`** — a spec from the `devcontainer.json` a repo already has.
  What it cannot translate is printed on stderr rather than silently dropped.
- **A waiting page** — a browser opening a sleeping link gets a page saying what is starting,
  instead of a white screen. Only after a second, only for an actual HTTP request, and it never
  delays the wake: **503 with the page at 1.00s, then 200 in 1.5ms on the reload.**

## Also new

- **`cap_add`** — grant a named Linux capability (`["SYS_PTRACE"]`) for the workloads whose
  failure names nothing you can act on. A list, never a `privileged` flag: privileged disables
  seccomp and AppArmor and hands over the host's devices, and sbx still does not offer it.
- **`--front NAME=HOST:PORT`** — a deployed sbx can now carry a service it can *route* to, not
  only one on its own loopback. That is how you reach a managed database on a private address from
  your laptop, over the one HTTPS port a platform gives you. It widens what the connect token
  gates — [SECURITY.md](../../SECURITY.md) says how.
- **A listing says when nothing owns the addresses it prints.** `sbx list` showed `awake` on ports
  that refuse when no daemon is running. Both were true and nothing on screen reconciled them.
- **The audit trail records who** slept or removed a sandbox, not only that it happened.

## Fixed

- **`sbx connect` truncated replies.** A client that shut its write side — `nc -N`, several HTTP
  clients, any bulk loader — had its response cut off, silently. Half-close now survives the
  tunnel.
- **A branching `depends_on` graph could kill the daemon**, taking every sandbox's ports with it.
  A parallel wake shared a map without a lock; every existing test used a chain, so nothing had
  ever branched.
- **A fork interrupted by `kill -9` could serve the wrong data.** Volumes are now filled before
  the containers exist.
- **`sbx create` was broken on kubernetes**, and `sbx url --via ssh` refused to run at all.
- **`sbx list | grep -q` exited 141.** A SIGPIPE, in a script that had done nothing wrong.
- **`sbx ui` went stale and misreported a cluster.**
- **A refused `egress_allow` left a half-built sandbox** that nothing could collect.
- **The test suite did not compile on Windows** — CI cross-compiled only the main package and
  never vetted, so a broken test suite there was invisible. All eight targets now build *and* vet.

## Upgrading

**No `sandbox.json` needs editing.** Two behaviours differ, and both are visible when they happen:

- `sbx url` rewrites the Host header by default — `--host-header pass` restores the old behaviour.
- `egress_allow` no longer needs `egress: "deny"` beside it, and no longer refuses on a Mac.

A stack that carried `idle: "never"` to work around the sleep problem can drop it.

```sh
brew upgrade sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | sh
go install github.com/aryanmehrotra/sbx@v0.8.0
```
