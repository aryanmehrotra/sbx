# sbx v0.9.0 — run OpenSandbox SDK code locally: `sbx serve` speaks the OpenSandbox API

Released 2026-09-26.

> Update (2026-09-26): upgrade to v0.9.1. v0.9.0 served a loopback `--osb-addr` without a key,
> and on colima and Docker Desktop any sandbox could drive the API. On v0.9.0, always pass
> `--osb-key`. See the [advisory](https://github.com/aryanmehrotra/sbx/blob/v0.9.1/SECURITY.md#advisories).

Code written against OpenSandbox's SDKs (Go, Python, JavaScript, Kotlin, C#), its `osb` CLI and
its MCP server now runs against sbx, with one binary and a docker engine. OpenSandbox is an open
API for agent sandboxes. The API is off unless you pass `--osb-addr`.

## Before you upgrade

- Breaking (Kubernetes): a service with `egress_allow` is refused on Kubernetes, where it was
  silently ignored. Do this: remove `egress_allow` from specs you deploy to a cluster.

## Highlights

```sh
sbx serve --osb-addr 127.0.0.1:8080 --osb-key "$OPEN_SANDBOX_API_KEY" &
claude mcp add sbx -- sbx mcp          # the same 19 tools as OpenSandbox's MCP server
```

- Lifecycle API (`/v1`): create, list, get, delete, metadata, pause/resume, renew-expiration, endpoints, network policy.
- In every sandbox: commands (streamed or background), persistent bash sessions, files, metrics. It needs only `/bin/sh`.
- `timeout` becomes an absolute `expiresAt` that survives a daemon restart.
- Network policy (domain, `*.wildcard`, IP, CIDR) changes on a running sandbox, through the API or `sbx egress`.
- `sbx serve --only PREFIX` runs a second daemon that touches only its own sandboxes.
- Idle API sandboxes freeze: memory is kept, no CPU is used, the next request thaws them.
  `extensions: {"sbx.idle": "sleep"}` stops them to 0 B instead.
- OpenSandbox's own Go e2e suite passes unmodified in CI: 36 passed, 0 failed, 2 skipped (upstream's).
  Run it: `scripts/osb-conformance.sh --docker-host <an engine with no sandboxes on it>`.

## Known limitations

- Security (fixed in v0.9.1): see the update at the top.
- Freezing holds memory. Use `sbx.idle: sleep` where 0 B matters more.
- The in-sandbox agent must match your sbx version. Without `SBX_EXECD_BINARY`, Linux, `go` or
  network access to the activator image, sbx cannot create API sandboxes, and says so.
- One operator key, no tenants, by design:
  [DECISIONS.md](https://github.com/aryanmehrotra/sbx/blob/v0.9.0/docs/DECISIONS.md).
- Not implemented: snapshots and templates, code interpreter, PTY, isolated sessions, credential
  vault. They answer `501`, never a `200` that did nothing.

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.9.0 sh
go install github.com/aryanmehrotra/sbx@v0.9.0
sbx doctor
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached with `SHA256SUMS`.
Cluster activator: `ghcr.io/aryanmehrotra/sbx-activator:v0.9.0`.
