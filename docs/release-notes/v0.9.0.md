## OpenSandbox's API, on the machine you already have

**v0.9.0 makes `sbx serve` speak OpenSandbox.** Code written against OpenSandbox's SDKs — Go,
Python, JavaScript, Kotlin, C# — its `osb` CLI, and its MCP server now runs against sbx with no
FastAPI server, no database and no Kubernetes: one binary and a docker engine.

"Compatible" is not a claim from a feature table. It is **OpenSandbox's own Go e2e suite, at
`release-1.1.0` (commit `b1a29cf`), fetched and run unmodified against sbx**:

```
scripts/osb-conformance.sh      # the v0.9.0 tier
36 passed, 0 failed, 2 skipped, 0 did not run - CONFORMANT for the selected tests
```

The two skips are upstream's own: both pause/resume tests call `t.Skip` unconditionally at that
tag. The harness fails a run on any skip it has not been told about, by test and by message, so a
skip cannot hide a failure. The job runs in CI on every push to `main` and every pull request.

---

## Try it

```sh
sbx serve --osb-addr 127.0.0.1:8080 &          # loopback; no key needed there
```

```go
sb, _ := opensandbox.CreateSandbox(ctx, opensandbox.ConnectionConfig{Domain: "localhost:8080"},
    opensandbox.SandboxCreateOptions{Image: "python:3.11-slim"})
out, _ := sb.RunCommand(ctx, "python -c 'print(6*7)'", nil)
```

Or skip the SDK and give an agent the tools directly:

```sh
claude mcp add sbx -- sbx mcp                 # the same 19 tools as OpenSandbox's MCP server
```

## What is in it

| | |
|---|---|
| **Lifecycle API** (`/v1`) | create, list, get, delete, metadata, pause/resume, renew-expiration, endpoints, network policy, diagnostics, metrics events |
| **execd, inside every sandbox** | commands (streamed or background, with status, logs and interrupt), persistent bash sessions, the whole file and directory API, metrics and a metrics stream |
| **Expiry** | `timeout` becomes an absolute `expiresAt` that survives a daemon restart; renew must move it later; a reaper removes what expired and says so in `sbx history` |
| **Network policy, live** | domain, `*.wildcard`, IP and CIDR rules, changed on a running sandbox without restarting it — through the API, the SDK's egress sidecar calls, or `sbx egress` |
| **`sbx mcp`** | an MCP server on stdio, speaking MCP 2024-11-05 through 2025-11-25 |
| **`sbx serve --only PREFIX`** | a daemon that touches only the sandboxes it is scoped to — the way to run a second one beside yours |

execd is sbx itself: the same static binary, placed in a read-only volume at `/opt/sbx` and run as
the sandbox's entrypoint wrapper. It reaps children and forwards signals, so your entrypoint still
behaves as PID 1 would, and it needs nothing from the image but `/bin/sh` for its health check.

## Where it goes past OpenSandbox

**An idle sandbox is frozen, not running.** After the idle timer an API sandbox is paused with
the cgroup freezer; the next request thaws it. Memory and running processes are kept — a
background command is still there — and it uses no CPU while nobody talks to it.
`extensions: {"sbx.idle": "sleep"}` stops it instead, to 0 B.

**Pause keeps memory** on docker, which OpenSandbox's docker runtime does not.

**Every existing sbx sandbox is unaffected.** The API is off unless you pass `--osb-addr`, and
nothing about how a `sandbox.json` sandbox wakes or sleeps has changed.

---

## What it costs you

- **Freezing holds memory.** That is the trade for keeping processes alive, and it applies only to
  sandboxes created through the API. Opt into `sleep` where 0 B matters more.
- **execd must match your sbx version.** sbx finds a linux binary in this order: `SBX_EXECD_BINARY`,
  itself on linux, a cross-compile when `go` is installed, then this release's activator image.
  A machine with none of those — no Go, no network — cannot create API sandboxes, and is told so.
- **One key, not users.** `--osb-key` is a single operator key; any address but loopback refuses
  to start without one. There are no tenants and there will not be — see
  [DECISIONS.md](../DECISIONS.md), which records the amendment this release makes.
- **Kubernetes now refuses a filtered service** rather than ignoring `egress_allow` without
  saying so. If you deploy a spec with an allow-list to a cluster, that create now fails with a
  message; it was never enforced there.
- Not yet: snapshots and templates through the API, the code interpreter, PTY, isolated sessions,
  credential vault. They answer `501` with the release that adds them, never a `200` that did
  nothing.

## Adopting it

```sh
brew upgrade sbx          # or: go install github.com/aryanmehrotra/sbx@v0.9.0
sbx serve --osb-addr 127.0.0.1:8080
```

To check it on your own machine: `scripts/osb-conformance.sh --docker-host <an engine with no
sandboxes on it>`. It refuses to run beside your own sandboxes, on purpose.
