# sbx v0.9.0 — run OpenSandbox SDK code locally: `sbx serve` speaks the OpenSandbox API

Released 2026-09-26.

> **Update (2026-09-26): upgrade to v0.9.1.** v0.9.0 served a loopback `--osb-addr` without a
> key. On colima and Docker Desktop every container reaches the host's loopback, so any sandbox
> could drive the API. On v0.9.0, always pass `--osb-key`. See the
> [advisory](https://github.com/aryanmehrotra/sbx/blob/v0.9.1/SECURITY.md#advisories).
> These notes were edited after release to add this warning; an earlier edit had also changed
> the example below to v0.9.1 behaviour, which has been put back.

Code written against OpenSandbox's SDKs (Go, Python, JavaScript, Kotlin, C#), its `osb` CLI and
its MCP server now runs against sbx: one binary and a docker engine, no FastAPI server, database
or Kubernetes. Existing `sandbox.json` sandboxes are unaffected; the API is off unless you pass
`--osb-addr`.

## Before you upgrade

- **Breaking (Kubernetes):** a service with `egress_allow` is now refused on Kubernetes instead
  of being created with the allow-list silently ignored. It was never enforced there.
  **Do this:** remove `egress_allow` from specs you deploy to a cluster, or run them elsewhere.

## Highlights

### Serve the OpenSandbox API with `sbx serve --osb-addr`

```sh
sbx serve --osb-addr 127.0.0.1:8080 --osb-key "$OPEN_SANDBOX_API_KEY" &
```

```go
sb, _ := opensandbox.CreateSandbox(ctx, opensandbox.ConnectionConfig{Domain: "localhost:8080"},
    opensandbox.SandboxCreateOptions{Image: "python:3.11-slim"})
out, _ := sb.RunCommand(ctx, "python -c 'print(6*7)'", nil)
```

- **Lifecycle API (`/v1`):** create, list, get, delete, metadata, pause/resume,
  renew-expiration, endpoints, network policy, diagnostics, metrics events.
- **execd in every sandbox:** commands (streamed or background, with status, logs and
  interrupt), persistent bash sessions, the file and directory API, metrics.
- **Expiry:** `timeout` becomes an absolute `expiresAt` that survives a daemon restart. Expired
  sandboxes are removed and logged in `sbx history`.
- **Live network policy:** domain, `*.wildcard`, IP and CIDR rules, changed on a running sandbox
  through the API, the SDK's egress calls, or `sbx egress`.
- **`sbx serve --only PREFIX`:** a daemon that touches only the sandboxes it is scoped to, so you
  can run a second one beside yours.

execd is the sbx binary itself, mounted read-only at `/opt/sbx`. It reaps children and forwards
signals, and needs only `/bin/sh` in the image.

### Proven with upstream's own test suite

OpenSandbox's Go e2e suite at `release-1.1.0` (commit `b1a29cf`), fetched and run unmodified:

```
scripts/osb-conformance.sh      # the v0.9.0 tier
36 passed, 0 failed, 2 skipped, 0 did not run - CONFORMANT for the selected tests
```

Both skips are upstream's (the pause/resume tests call `t.Skip` unconditionally at that tag). Any
unexpected skip fails the run. It runs in CI on every push to `main` and every pull request.

### Give an agent the same tools with `sbx mcp`

```sh
claude mcp add sbx -- sbx mcp          # the same 19 tools as OpenSandbox's MCP server
```

An MCP server on stdio, speaking MCP 2024-11-05 through 2025-11-25.

### Idle API sandboxes freeze instead of running

After the idle timer, an API sandbox is paused with the cgroup freezer: memory and processes are
kept, no CPU is used, and the next request thaws it. `extensions: {"sbx.idle": "sleep"}` stops
it instead, to 0 B. Pause also keeps memory on docker, which OpenSandbox's docker runtime does
not.

## Known limitations

- **Security (fixed in v0.9.1):** see the update at the top.
- **Freezing holds memory.** That is the trade for keeping processes alive; it applies only to
  API sandboxes. Use `sbx.idle: sleep` where 0 B matters more.
- **execd must match your sbx version.** sbx looks for a Linux binary in order:
  `SBX_EXECD_BINARY`, itself on Linux, a cross-compile if `go` is installed, then this release's
  activator image. With none of those (no Go, no network) it cannot create API sandboxes, and
  says so.
- **One key, not users.** `--osb-key` is a single operator key; a non-loopback address refuses
  to start without one. There are no tenants, by design; see
  [DECISIONS.md](https://github.com/aryanmehrotra/sbx/blob/v0.9.0/docs/DECISIONS.md).
- **Not implemented:** snapshots and templates, code interpreter, PTY, isolated sessions,
  credential vault. They answer `501`, never a `200` that did nothing. (The v0.9.0 messages named
  a release that would add them; that was removed in v0.13.2 because those releases did not.)

## Upgrade

```sh
brew upgrade sbx                  # first install: brew install aryanmehrotra/tap/sbx
curl -fsSL https://raw.githubusercontent.com/aryanmehrotra/sbx/main/scripts/install.sh | VERSION=v0.9.0 sh
go install github.com/aryanmehrotra/sbx@v0.9.0
sbx doctor                        # checks this machine can run what you use
```

Binaries for macOS, Linux, FreeBSD and Windows (amd64, arm64) are attached below with
`SHA256SUMS`; `install.sh` verifies them. Cluster activator:
`ghcr.io/aryanmehrotra/sbx-activator:v0.9.0`.

To run the conformance suite yourself:
`scripts/osb-conformance.sh --docker-host <an engine with no sandboxes on it>`. It refuses to
run beside your own sandboxes.
